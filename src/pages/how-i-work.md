# How I work

문서 한 편을 잘 쓰는 것보다, 좋은 문서가 반복해서 나오는 구조를 만드는 데 관심이 있습니다. 이 페이지는 제가 실제로 쓰는 기준과 도구를 정리한 것입니다.

## 1. 정보 설계

### 독자를 먼저 정의합니다

문서를 시작하기 전에 세 가지를 확정합니다. 확정되지 않으면 초안을 쓰지 않습니다.

| 항목 | 질문 |
| --- | --- |
| 독자 | 누가 읽는가. 사전 지식은 어디까지 있는가 |
| 목적 | 독자가 이 문서로 무엇을 해결하는가 |
| 깊이 | 개념 이해용인가, 작업 수행용인가, 검색용 레퍼런스인가 |

### 문서 유형을 나눕니다

Diátaxis 프레임워크를 기본 체계로 사용합니다.

| 유형 | 목적 | 이 사이트의 예 |
| --- | --- | --- |
| 튜토리얼 | 처음 해보는 사람을 끝까지 데려간다 | 센서 설치하기 |
| 하우투 가이드 | 목적이 분명한 사람이 작업을 끝낸다 | 콘솔 시작하기 |
| 레퍼런스 | 필요한 항목을 찾아본다 | API 인증 |
| 설명 | 왜 그런지 이해한다 | 각 문서의 설계 노트 |

유형이 섞이면 문서가 길어지고 아무도 끝까지 읽지 않습니다. 한 페이지에는 한 유형만 담습니다.

## 2. 품질 기준과 자동화

문서 리뷰에서 반복해서 지적하게 되는 항목은 사람이 계속 볼 일이 아니라 시스템으로 옮겨야 한다고 생각합니다. 검사의 성격에 따라 도구를 나눴습니다.

| 검사 | 도구 | 이유 |
| --- | --- | --- |
| 깨진 링크·앵커·이미지 | 스크립트 | 정답이 명확하고, 빠르고, 결과가 항상 같음 |
| 금지 표기 (용어집 대조) | 스크립트 | 기계적으로 확실히 잡힘 |
| 오탈자·문법 | AI 리뷰 | 문맥 판단이 필요 |
| 문체·스타일 가이드 준수 | AI 리뷰 | 규칙만으로 판정하기 어려움 |
| 번역 품질 (직역투·의미 왜곡) | AI 리뷰 | 두 언어의 뉘앙스 비교가 필요 |

핵심 설계는 **로직과 설정의 분리**입니다. 스타일 룰과 용어집을 설정 파일로 두면, 회사가 달라져도 설정만 교체하면 같은 도구가 동작합니다.

검사는 문서를 수정한 PR이 열릴 때 실행되도록 구성합니다. 사람이 기억해서 돌리는 검사는 결국 돌지 않기 때문입니다.

## 3. 다국어 운영

번역을 새로 하는 것보다 **원문과 번역본이 어긋나지 않게 유지하는 것**이 더 어렵다고 봅니다. 그래서 두 가지를 함께 관리합니다.

- **용어집**: 언어 쌍별 표준 용어와 금지 표기를 한 파일로 관리합니다.
- **버전 드리프트 감지**: 원문이 갱신됐는데 번역본이 그대로인 문서를 찾아 표시합니다.

번역 검수에서 가장 가치 있는 발견은 번역 오류가 아니라 **원문이 애매해서 번역이 갈리는 문장**입니다. 이런 문장은 번역본을 고치는 대신 원문을 고칩니다.

## 4. 문서가 낡지 않게 하는 법

문서는 쓰는 순간이 아니라 방치되는 동안 망가집니다. 그래서 문서마다 다음을 정합니다.

- 검토 주기 (기본 90일)
