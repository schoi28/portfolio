# 실무 경험

자율주행 소프트웨어 회사에서 영문·국문 기술 문서를 담당하고 있습니다. 흩어져 있던 제품 문서를 하나의 솔루션 문서 세트로 묶고, **그 문서를 만들고 검수하는 도구를 직접 개발**했습니다.

:::note
실무 산출물은 대외비라 문서와 코드를 공개할 수 없습니다. 이 페이지는 **무엇을 판단하고 어떻게 만들었는지**를 기록한 것입니다. 같은 구조의 문서 세트를 가상 제품으로 재현해 [Work](/work)에 공개했습니다.
:::

| 항목 | 규모 |
| --- | --- |
| 제품 | 5종 (2개 솔루션으로 묶여 판매) |
| 문서 | 마크다운 460여 편, 이미지 870여 장 |
| 버전 관리 | 제품별 릴리스 2~3개 + 개발 버전 트리 |
| 포맷 | 웹(정적 HTML) · PDF, 단일 소스에서 생성 |
| 직접 개발한 도구 | 정적 사이트 생성기, 검수 도구, API 문서 생성기, 빌드 GUI |

## 0 → 1: 통합 솔루션 문서 세트 구축

### 상황

제품들이 솔루션으로 묶여 판매되는데, 문서는 그 형태로 존재하지 않았습니다.

| 제품 | 기존 문서 상태 |
| --- | --- |
| 라이다 인지 엔진 | 개발자가 작성한 Google Docs 매뉴얼. 코멘트가 한눈에 보이지 않아 리뷰가 정체되어 있었습니다 |
| 운영 애플리케이션 | 없음. 입사 후 개발이 시작된 제품이라 UI 요소의 이름부터 정해야 했습니다 |
| 모션 플래닝 소프트웨어 | 클라이언트에 전달하던 5페이지 내외의 비공식 퀵 가이드만 있었습니다 |
| 솔루션 전체 | 제품들을 묶어 설명하는 문서는 없었습니다 |

### 한 일

**라이다 인지 엔진** — 포맷을 Markdown으로 전환하고 리뷰를 GitHub Pull Request에서 받는 구조로 바꿨습니다. SDK 문서와 API 문서까지 범위에 포함했습니다.

**운영 애플리케이션** — 정보 구조 설계부터 시작해 전체를 집필했습니다. 기획 회의에 참여해 UI 네이밍에도 관여했습니다. 운영자가 구역과 차량, 시스템 상태를 모니터링하는 제품이라 단계별 절차 가이드와 이미지 작업의 비중이 컸습니다.

**모션 플래닝 소프트웨어** — 제품 중 기술적 깊이가 가장 깊었습니다. 이 문서를 쓰면서 용어집 정책을 만들고, 이후 모든 매뉴얼의 공통 정책으로 적용했습니다.

**솔루션 매뉴얼** — 솔루션 전체를 설명하는 문서를 새로 썼습니다. 비즈니스 관점의 개괄 설명과, 운영자를 위한 핵심 개념 다이제스트·운영 절차·트러블슈팅을 담당했습니다.

### 판단한 것들

#### 하나로 묶을 것인가, 제품별로 둘 것인가

**둘 다 선택했습니다.** 문서 세트를 2층 구조로 설계했습니다.

```
솔루션 매뉴얼
├── 비즈니스 관점 개괄          ← 도입을 검토하는 독자
└── 운영자용 핵심 개념·운영·트러블슈팅   ← 솔루션을 운영하는 독자
제품별 사용자 매뉴얼 × 3
└── 각 제품의 상세               ← 제품을 직접 다루는 독자
```

근거는 두 가지였습니다.

- **고객사마다 제공되는 솔루션 구성이 다릅니다.** 전체를 도입하는 고객사와 일부만 도입하는 고객사가 있었습니다.
- **일부 제품은 단독 판매가 가능합니다.** 인지 엔진은 솔루션에 포함되기도 하고 단독으로 쓰이기도 했습니다.

그래서 **네 부분을 따로 빌드하거나 합쳐서 빌드할 수 있게** 만들었습니다. 문서 구조가 판매 구조를 따라가야 한다고 판단했고, 그 유연성을 문서가 아니라 빌드 도구로 확보했습니다.

#### 웹과 PDF를 어떻게 함께 유지할 것인가

**오프라인 동작이 요건이었습니다.** 배포 환경의 네트워크가 불안정할 수 있어, 인터넷 연결 없이 온전히 열리는 매뉴얼이 필요했습니다. 그래서 웹 매뉴얼은 정적 HTML로 만들어 소프트웨어에 함께 패키징하거나 파일로 전달했습니다.

PDF는 기존 관행이었습니다. PDF 형태에 익숙한 고객사가 이미 있었기 때문에, 웹 매뉴얼을 추가로 제공하는 형태로 자연스럽게 정착했습니다.

두 포맷을 따로 관리하면 반드시 어긋납니다. 단일 소스에서 두 포맷을 생성하는 구조를 선택했습니다.

#### 독자를 어떻게 나눌 것인가

B2B 제품이라 독자를 책상에서 추측할 수 없었습니다. 실제 프로젝트를 고객사와 함께 진행하면서 **각 제품에 어떤 직무의 담당자가 접근하는지 조사**하고, 그 결과를 고객사에 종속되지 않는 일반적인 유형으로 변환했습니다.

최종적으로 세 계층으로 정리했습니다.

| 계층 | 유형 | 전제하는 사전 지식 |
| --- | --- | --- |
| 이해 | 일반 독자 — 솔루션이 무엇이고 도입에 무엇이 필요한지 알고자 하는 사람 | 없음 |
| 운영 | 관리자 · 운영자 · 조회자. 현장 운영자와 원격 운전자 포함 | 기본적인 컴퓨터 활용 능력과 소프트웨어 UI 사용 경험 |
| 기술 | 현장 적용 엔지니어 · 차량 측 통합 엔지니어 · 소프트웨어 개발자 · IT 관리자 | 역할별로 다름. Linux 명령줄과 네트워크, 차량 컨트롤러 통합, REST API와 JSON, 시스템 관리 |

이 표를 만들면서 정한 것들이 있습니다.

**유형마다 어디서부터 읽을지 지정했습니다.** 역할 표에 "관련 섹션" 열을 두고 시작 지점을 링크로 연결했습니다. 독자가 자기 역할을 찾으면 읽을 범위가 함께 정해집니다. 위 세 번째 원칙을 문서의 입구에서 먼저 적용한 것입니다.

**문서의 독자 유형과 제품의 권한 등급을 분리했습니다.** 둘은 다릅니다. 권한 등급은 소프트웨어 설정이고, 독자 유형은 읽기 안내입니다. 섞으면 "내 계정은 조회 권한인데 운영자 문서를 읽어도 되는가" 같은 혼란이 생깁니다. 그래서 역할 표에 **이 표는 읽기 안내이며 계정 권한의 정의가 아니라는 설명**을 명시했고, 권한이 필요한 작업은 본문에서 그 자리에 표시했습니다.

**고객사마다 조직 구조가 다른 문제를 문서에서 처리했습니다.** 같은 일을 하는 직무의 이름이 고객사마다 다릅니다. 유형은 일반적인 이름으로 쓰고, 현장의 역할 이름과 정확히 일치하지 않을 수 있으니 가장 가까운 행을 참고하라는 안내를 넣었습니다.

**사전 지식의 기준선을 전 제품에서 동일하게 선언했습니다.** "자율주행 시스템에 대한 사전 지식은 전제하지 않는다"를 공통 기준으로 두고, 역할별 추가 전제만 다르게 기술했습니다. 이 기준선이 **용어집 정책이 작동하는 근거**입니다. 어떤 용어가 "독자 수준에 맞지 않는가"를 판단하려면 비교할 기준이 있어야 하기 때문입니다.

문서 간 선후 관계도 함께 밝혔습니다. 운영자 문서는 개괄 문서의 개념을 전제한다고 명시해, 독자가 어느 순서로 읽어야 하는지 알 수 있게 했습니다.

이 판단 방식을 정리한 것이 [How I work](/how-i-work)이고, 가상 제품에 적용한 결과가 [Work](/work)의 네 문서 세트입니다.

### 결과

**리뷰가 정체되지 않게 되었습니다.** 기능 담당자를 따로 찾아 핑할 필요 없이, 개발자에게 익숙한 형태로 리뷰를 받게 되면서 대부분의 리뷰가 1~2일 안에 끝납니다. diff로 변경 지점을 바로 확인할 수 있어 비교가 직관적이라는 평을 받았습니다. 소량 업데이트를 위한 잦은 리뷰 요청이 오히려 커뮤니케이션의 질을 높였습니다.

**버전 추적성이 개선되었습니다.** 드라이브에서 매뉴얼 폴더와 버전을 찾는 방식에서, 브랜치별로 해당 시점의 파일 버전을 관리하는 방식으로 바꿨습니다.

**동시 작업이 가능해졌습니다.** 최종 리뷰에서 확인할 지점을 목록으로 만들어 그 부분에 피드백을 집중하고, 웹과 PDF를 동시에 빌드하도록 바꿔 3~4개 제품 작업을 병행할 수 있게 되었습니다.

**온보딩 자료로 쓰이고 있습니다.** 특히 웹 매뉴얼의 검색 기능으로 현장 배포·필드 애플리케이션 엔지니어가 필요한 정보에 빠르게 접근할 수 있다는 피드백을 받았습니다.

## 문서 품질 기준 수립

문서를 쓰는 것과 별개로, **좋은 문서의 조건을 기준으로 만들어 전체에 적용**했습니다.

### 세 가지 절대 원칙

제품과 작성자가 달라도 지키도록 정한 규칙입니다.

1. **미리 정의한 독자 수준에 맞지 않는 용어는 예외 없이 용어집에 넣는다.** 기술 깊이가 가장 깊은 문서를 쓰면서 이 정책을 만들고, 이후 모든 매뉴얼의 공통 정책으로 적용했습니다.
2. **개념과 절차를 섞지 않는다.** 불가피한 경우를 제외하고 분리합니다.
3. **목적에 따라 바로 찾아갈 수 있도록 목차를 구성한다.** 제품 기능 순서가 아니라 독자의 목적 순서로 배열합니다.

전체 매뉴얼의 구조는 **IEC/IEEE 82079-1**(사용 설명서 작성에 관한 국제 표준)을 참조해 재정비했습니다.

### 기여자용 가이드 작성

기준을 문서로 만들어 두지 않으면 지켜지지 않습니다. 다른 사람이 문서 작업에 참여할 수 있도록 가이드 두 종을 작성했습니다.

| 가이드 | 내용 |
| --- | --- |
| 설정 가이드 | 새 버전·제품·솔루션·기능을 추가하는 시나리오, 내비게이션 설정 레퍼런스, 조건부 콘텐츠 마커 사용법 |
| 작성 가이드 | 마크다운 문법, 이미지 처리, 용어집 툴팁 적용, 용어집 정리 |

설정 가이드는 기능 목록이 아니라 **"무엇을 하려는가" 기준의 시나리오**로 구성했습니다. 위 세 번째 원칙을 제 도구의 문서에도 적용한 결과입니다.

## 문서 빌드·검수 도구 직접 개발

처음에는 공개 정적 사이트 생성기(MkDocs)를 쓰려 했습니다. 커스터마이징할 항목이 계속 늘어나 **자체 개발로 전환**했습니다. 현재 JavaScript 약 5,800줄 규모이고, 별도의 Python 도구가 있습니다.

### 웹·PDF 동시 빌드

- 단일 소스에서 브랜드 가이드라인이 적용된 정적 HTML 사이트와 PDF를 생성합니다.
- PDF는 렌더링 후 압축을 적용해 용량을 약 44% 줄였습니다. 이미지도 빌드 단계에서 최적화합니다.
- 산출물은 **완전 오프라인에서 동작**합니다.
- 제품 단위, 솔루션 단위, 전체 빌드를 지원하고, 솔루션 빌드에서 **특정 제품만 개발 버전으로 미리보는 오버라이드**를 넣었습니다. 개발 버전이 자동으로 선택되는 일은 없도록 기본값을 설계했습니다.

### 고객사별 조건부 콘텐츠 시스템

고객사마다 제공되는 기능이 달랐습니다. 같은 소스로 여러 산출물을 만들 때, **어떤 고객사 문서에 어떤 내용이 들어가는지를 사람이 기억하는 방식**은 유지되지 않습니다. 빠뜨리면 고객이 기능을 모르고, 잘못 넣으면 다른 고객의 정보가 노출됩니다.

그래서 노출 범위를 문서 안에 선언하고 빌드가 판단하도록 바꿨습니다. 축은 세 개입니다.

| 축 | 용도 |
| --- | --- |
| 고객사 | 고객사 전용 내용 |
| 내부 | 내부 전용 내용 |
| 기능 | 기능 단위 노출 제어. 기능 × 고객사 행렬을 설정 파일로 관리 |

적용 수준도 세 단계로 나눴습니다. 마크다운 안의 **섹션 수준** 마커, 내비게이션 설정의 **페이지 수준** 필터, 챕터별 **웹 전용·PDF 전용** 제어입니다.

### 검수 도구

약 1,000줄 규모로, 세 가지를 검사합니다.

| 검사 | 내용 |
| --- | --- |
| 내부 링크·앵커 | 대상 파일이 존재하는지, 지정한 앵커가 실제로 있는지 확인합니다. 파일 간 교차 검증을 지원합니다 |
| 조건부 마커 구조 | 노출 제어 마커가 구조적으로 올바른지 검증합니다 |
| **산출물과 선언 범위의 일치** | 빌드 결과가 선언한 고객사 범위와 일치하는지 확인합니다 |

세 번째가 핵심입니다. **다른 고객사의 정보가 산출물에 섞여 들어가지 않았음을 빌드가 기계적으로 보장**합니다. 사람의 기억에 의존하던 일을 검증 가능한 구조로 옮겼습니다.

전체·제품 단위·제품과 버전 단위로 범위를 지정할 수 있고, 빌드 과정에서 자동 실행되는 것과 별개로 단독 실행도 지원합니다.

설계에서 한 가지 의도적으로 제한한 부분이 있습니다. 설정 목록의 앵커가 어긋나는 문제는 **자동으로 고치지 않고 보고만** 합니다. 문서를 임의로 변경하는 도구는 신뢰를 잃는다고 판단했습니다.

### 용어집 툴팁 시스템

웹 매뉴얼은 독자의 진입 위치가 고정되지 않습니다. 검색으로 중간 페이지에 바로 들어온 독자도 용어 때문에 막히지 않아야 합니다.

용어집 페이지의 표를 읽어 용어와 설명을 짝지은 뒤, 같은 제품의 모든 페이지에서 **각 용어의 첫 등장에 호버 툴팁을 붙이도록** 만들었습니다. 팝업이 상위 표나 컨테이너에 잘리지 않도록 위치를 계산합니다.

설계에서 정한 것들입니다.

- **옵트인 전용**: 용어집 표에 표시가 있는 용어만 툴팁이 붙습니다. 기본 포함 목록을 두면 "빼고 싶은 용어"와 계속 싸우게 됩니다.
- 표시는 렌더링 결과에 보이지 않으면서 유지되어야 합니다. 파서를 통해 실제로 그렇게 동작하는지 확인했습니다.
- 용어집 파일을 **위치가 아니라 이름으로** 찾습니다. 부록 순서를 바꿔도 깨지지 않습니다.

작성 시점에는 별도 린터로 용어집의 정렬·교차 참조·중복을 검사하고, 자동 정리 옵션을 제공합니다.

### API 레퍼런스 자동 생성

API 스키마와 설정값 목록은 손으로 유지하면 반드시 실제 제품과 어긋납니다. 정확하게 쓰려고 노력하는 것보다 **틀릴 수 없는 구조를 만드는 쪽**이 확실하다고 판단했습니다.

OpenAPI 스펙에서 엔드포인트 문서와 스키마 문서를 생성하는 파이프라인을 만들었습니다. 핵심은 **변경 리포트**입니다.

- 엔드포인트: 추가 · 삭제 · 파라미터 변경 · 응답 코드와 설명 변경
- 스키마: 추가 · 삭제 · 제목과 설명 변경 · 속성 변경 · 타입 변경 · 제약 조건 변경 · enum 값 변경

생성 결과를 기존 문서에 그대로 덮어써도 안전하도록 설계했습니다. 무엇이 바뀌었는지 먼저 확인한 뒤 반영할 수 있습니다.

### 빌드 GUI

도구를 저만 쓰면 의미가 절반입니다. 명령줄을 쓰지 않는 구성원도 빌드할 수 있도록 웹 GUI를 만들었습니다.

- 솔루션·제품 선택, 제품별 버전 선택
- 기본값은 "개발 버전을 제외한 최신 릴리스"로 서버에서 계산해 내려줍니다
- 빌드와 검사가 동시에 실행되지 않도록 잠금 처리, 잘못된 요청은 사전 검증으로 차단

### AI를 어떻게 썼는가

구현은 AI와 함께 했습니다. 중요한 것은 **무엇을 맡기고 무엇을 직접 판단했는가**입니다.

제가 판단한 것들입니다.

| 판단 | 내용 |
| --- | --- |
| 조건부 콘텐츠 축 설계 | 고객사·내부·기능 세 축으로 나눈 것, 섹션·페이지·포맷 세 수준으로 적용한 것 |
| 마커 문법 | 마크다운 안에서 쓸 주석 형식 |
| 검수 항목 선정 | 무엇을 검사할지, 특히 산출물과 선언 범위의 일치를 검사 대상에 넣은 것 |
| 자동 수정의 경계 | 앵커 드리프트는 고치지 않고 보고만 하도록 제한한 것 |
| 용어집 옵트인 원칙 | 기본 포함 목록을 두지 않는다는 결정 |
| 파일 탐색 방식 | 위치가 아니라 이름으로 찾도록 한 것 |
| 기본 버전 선택 규칙 | 개발 버전이 자동 선택되지 않도록 한 것 |
| 도구 전환 판단 | MkDocs의 커스터마이징 한계를 확인하고 자체 개발로 전환한 것 |

AI에 맡긴 것은 구현, 파싱 로직, 빌드 스크립트입니다.

**검증은 생성 이후가 아니라 생성 조건으로 옮겼습니다.** 코드를 받아 놓고 문제를 찾는 대신, **예상되는 엣지 케이스를 먼저 목록으로 만들어 그 목록을 통과하도록 명시적으로 지시**했습니다.

문서 도구의 엣지 케이스는 대체로 미리 적을 수 있습니다. 마커가 중첩된 경우, 용어가 표 안에 있는 경우, 앵커가 다른 파일을 가리키는 경우처럼 구조에서 예측되는 것들입니다. 이것을 요구사항으로 먼저 주면 검증이 사후 작업이 아니라 생성 조건이 됩니다.

엣지 케이스를 정확하게 적는 일 자체가 테크니컬 라이팅과 같은 작업이었습니다. 무엇이 입력이고 무엇이 예외인지 빠짐없이 쓰는 것이기 때문입니다.

### 결과

- 가장 큰 범위(솔루션 전체 + 통합 PDF)의 납품본이 **설정 변경 후 빌드 한 번으로 2분 내외에 완성됩니다.**
- 고객사별 납품 구성이 달라도 **문서를 손으로 재조립하지 않습니다.** 설정에서 범위를 지정하고 빌드합니다.
- 웹과 PDF를 **따로 만들지 않습니다.** 한 번의 빌드로 두 포맷이 나옵니다.
- **3~4개 제품의 문서 작업을 병행할 수 있습니다.** 납품본을 만드는 동안 다른 작업을 멈추지 않아도 됩니다.
- 고객사 간 정보 혼입을 **사람이 기억하지 않아도 됩니다.** 빌드가 검증합니다.
- 명령줄을 쓰지 않는 구성원도 빌드할 수 있습니다.

:::note
이 도구의 코드는 회사 자산이라 공개하지 않습니다. 구조와 설계 판단은 설명할 수 있습니다.
:::

## docs-as-code 전환

가장 먼저 한 일은 포맷과 리뷰 경로를 바꾸는 것이었습니다.

기존 매뉴얼은 Google Docs에 있었고, 코멘트가 한눈에 보이지 않아 리뷰가 정체되어 있었습니다. 문서를 Markdown으로 옮기고 리뷰를 **GitHub Pull Request**에서 받도록 바꿨습니다. 개발자가 이미 매일 쓰는 도구 안으로 문서 리뷰를 옮긴 것입니다.

현재 일상 작업 환경입니다.

- Markdown 기반 문서 작성
- Git · GitHub으로 버전 관리와 브랜치별 버전 추적
- Pull Request 리뷰로 개발자·기획자 피드백 수렴

이 사이트도 같은 환경에서 만들었습니다. Docusaurus로 작성하고 GitHub Actions로 빌드·배포하며, 깨진 링크가 있으면 빌드가 실패하도록 설정했습니다. 저장소는 [여기](https://github.com/schoi28/portfolio)에서 볼 수 있습니다.

## 그 전: docs-as-code 환경에서 익힌 것

2023년 11월부터 2024년 12월까지 DBMS 소프트웨어 회사에서 제품 매뉴얼 전반을 국문·영문으로 담당했습니다. 문서가 GitHub 공개 저장소([ALTIBASE/Documents](https://github.com/ALTIBASE/Documents))에서 관리되는 환경이었습니다.

이 시기의 작업은 **이미 있는 문서 체계 안에서 매뉴얼을 갱신하고 번역한 것**입니다. 체계를 설계한 경험은 그다음 회사에서 쌓았습니다.

| 항목 | 내용 |
| --- | --- |
| 기간 | 2023.12 ~ 2024.11 |
| 작업 방식 | 이슈 트래커의 요청 번호에 연결된 Pull Request 단위 작업, 리뷰 코멘트 반영 |
| 규모 | PR 113건 제출 / 101건 머지, 저장소 Collaborator |
| 문서 유형 | SQL 레퍼런스, API 사용자 매뉴얼, 복제·로그 분석기 매뉴얼, 도구 매뉴얼(마이그레이션 센터·iLoader·Precompiler), 설치 가이드, 릴리스 노트·패치 노트 |
| 이중 언어 | 영어 번역본이 없던 매뉴얼의 번역 수행, 이후 국문·영문 동시 갱신 |

레퍼런스와 가이드, 릴리스 노트를 모두 다뤘다는 점이 이후 작업에 도움이 되었습니다. 문서 유형마다 독자가 기대하는 것이 다르다는 감각을 이때 얻었습니다.

웹 매뉴얼은 MkDocs와 Read the Docs로 만들었습니다. 이 경험이 현 직장에서 자체 생성기를 만든 출발점이 되었습니다. MkDocs로 할 수 있는 것과 할 수 없는 것을 먼저 파악한 뒤, 오프라인 동작과 고객사별 조건부 콘텐츠가 필요해진 시점에 자체 개발로 전환했습니다.
