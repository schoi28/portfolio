# 실무 경험

자율주행 소프트웨어 회사에서 영문·국문 기술 문서를 담당하고 있습니다.

:::note
실무 산출물은 대외비라 문서 자체를 공개할 수 없습니다. 이 페이지는 **무엇을 판단하고 어떻게 만들었는지**를 기록한 것입니다. 같은 구조의 문서 세트를 가상 제품으로 재현해 [Work](/work)에 공개했습니다.
:::

## 0 → 1: 통합 솔루션 매뉴얼 구축

### 상황

세 개의 제품이 하나의 솔루션으로 묶여 판매되는데, 문서는 그 형태로 존재하지 않았습니다.

- 라이다 인지 엔진
- 플릿 관리 애플리케이션
- 자율주행 모션 플레닝 소프트웨어

[ ] 각 제품의 문서가 어떤 상태였는지 1~2줄. 예시: "제품별로 작성 주체와 포맷이 달라, 솔루션 전체를 설명하는 문서는 없었습니다."

라이다 인지 엔진 소프트웨어(H)의 경우, 기존 개발자가 쓴 구글 docs의 유저 매뉴얼이 있었음. 하지만 코멘트를 한눈에 보기 어려워서 정체된 리뷰가 많았던 상태.
플릿 관리 애플리케이션(O)은 입사 후 개발된 소프트웨어. 각 ui 요소 이름부터 지어야 했던 상황. 완전 0to1 작성
자율주행 모션 플래닝 소프트웨어(A)의 경우에도 클라이언트에게 주요 기능을 퀵 가이드로 전해주는 5페이지 내외의 비공식 문서만 있었던 상황

이 세 소프트웨어 스택으로 구성된 솔루션 매뉴얼 자체도 없었던 상황.

### 내가 맡은 범위

[ ] 예시: 통합 매뉴얼의 정보 구조 설계, 전체 집필, 웹·PDF 두 포맷의 빌드 구조 설계
내 히스토리를 알려줄테니까 네가 작성해봐:기존 H 유저 매뉴얼부터 우선 포맷을 마크다운으로 변경, 개발자와의 원활한 리뷰를 위해 깃헙 PR을 열어 점검을 받는 구조로 진행.
sdk 문서 및 api 문서 포함한 범위.
동시에 스태틱 html로 만든 웹 매뉴얼 사이트 제작 시작, 처음엔 기존의 오픈소스를 사용하려고 했고(mKdocs), 커스터마이징 할 것들이 많아져서 아예 자체 개발
웹/pdf 동시 빌드/배포 시스템을 구축함
O 유저매뉴얼 정보 구조 설계부터 시작하여 작성. 기획 회의에 참여하여 ui 네이밍에도 참여, 클라이언트가 전체 자율주행 에어리어와 차량, 시스템 상태를 모니터링하기 쉽도록 제공하는 어플리케이션이기 때문에 대량의 스텝바이스텝 가이드 위주 및 이미지 작업 포함.
A 유저 매뉴얼 작성과 함께 이 셋을 묶은 솔루션 매뉴얼까지 도큐먼트 셋(set)을 완성.
솔루션의 비즈니스적인 강점을 포함하여 개략적인 이해를 돕는 문서와 오퍼레이터 전용 트러블 슈팅 가이드를 포함한 파트를 작성.
A 유저 매뉴얼의 경우, 가장 기술 지식 깊이가 깊은 주제라서 이때 글로서리 정책을 만들어 모든 유저 매뉴얼에 공통 정책으로 만들어 적용.
모든 파일은 웹/pdf 전부 제공. 통합 솔루션 매뉴얼(솔루션 매뉴얼+각 프로덕트 매뉴얼들)까지 최종 빌드

진화된 툴: 단순 설정에 따른 웹/pdf 빌드 뿐만 아니라 회사 브랜드가이드라인들 따른 디자인, 각 클라이언트 별 피처 플래그 기능(마크다운 파일에 커스터마이징한 주석 포맷의 마크를 만들어 특정 클라이언트 dedicated하게 제공되는 기능이나 그에 관련한 설명이 다른 클라이언트에게 노출되지 않게 방지), 각종 검수 체커 툴 및 특정 포맷의 섹션(rest api schema reference 나 configuration list reference 등) 자동 업데이트 툴 생성.

모든 매뉴얼의 구조를 iso ??(그 소프트웨어 문서와 관련 국제 기준)에 맞게끔 리스토어링. 기본 절대 정책은 1. 미리 정해둔 intended ㄴaudience 수준에 맞지 않는 용어는 무조건 글로서리에 넣기, 2. 개념과 절차는 불가피한 경우가 아니고서는 섞지 않기, 3.목적에 따라 바로 찾아갈 수 있는 toc 구성하기

### 판단한 것들

문서를 쓰기 전에 결정해야 했던 것들입니다. 이 결정들이 결과물의 모양을 정했습니다.

#### 하나의 매뉴얼로 묶을 것인가, 세 개로 둘 것인가

[ ] 어느 쪽을 선택했고 왜 그랬는지. 독자가 솔루션을 통째로 도입하는지, 제품별로 도입하는지가 근거가 될 수 있습니다.

#### 독자를 어떻게 나눌 것인가

세 제품의 독자가 같지 않았습니다.

[ ] 독자를 몇 개 유형으로 정의했는지, 그 기준이 무엇이었는지.
    예시: 도입을 결정하는 사람 / 설치·통합하는 엔지니어 / 운영하는 담당자

독자 정의가 먼저 끝나야 같은 기능을 어느 깊이로 설명할지 정할 수 있었습니다. 이 판단 방식을 정리한 것이 [How I work](/how-i-work)이고, 가상 제품에 적용한 결과가 [Work](/work)의 네 문서 세트입니다.

#### 웹과 PDF를 어떻게 함께 유지할 것인가

두 포맷이 모두 필요했습니다. [ ] 각각 왜 필요했는지 1줄. 예시: 웹은 검색과 갱신, PDF는 납품과 오프라인 열람.

두 포맷을 따로 관리하면 반드시 어긋납니다. 단일 소스에서 두 포맷을 생성하는 구조를 선택했습니다.

### 결과

[ ] 무엇이 어떻게 바뀌었는지. 숫자가 없어도 됩니다. 다만 "누가 무엇을 덜 하게 되었는지"가 드러나야 합니다.

예시로 쓸 수 있는 축:
- 이전에는 OO을 물어보려면 OO을 거쳐야 했는데, 지금은 OO
- 제품별로 흩어져 있던 OO이 한 곳에서 확인 가능해짐
- 신규 입사자가 OO까지 걸리던 시간이 줄어듦
- 고객 문의 중 OO 유형이 줄어듦

## AI를 활용한 문서 빌드 파이프라인 구현

### 문제

매뉴얼을 납품할 때마다 반복되는 작업이 있었습니다.

[ ] 무엇이 반복 작업이었는지. 예시: 고객사마다 포함할 제품 구성이 달라, 그때마다 문서를 손으로 재조립하고 PDF를 다시 만들어야 했습니다.

### 만든 것

[ ] 무엇을 자동화했는지. 코드는 공개하지 않고 구조만 서술합니다.

서술할 수 있는 축:
- 입력: 무엇을 설정하면 되는가 (어떤 제품 구성, 어떤 포맷)
- 처리: 단일 소스에서 무엇을 어떻게 생성하는가
- 출력: 웹 / PDF
- 커스터마이징: 회사·고객사 상황에 맞게 바꿀 수 있게 만든 부분

### AI를 어떻게 썼는가

[ ] 중요한 항목입니다. JD가 "AI를 활용한 문서화 경험이 있다면 구체적으로 적어주세요"라고 명시합니다.

구체적으로 쓸 축:
- 내가 설계한 부분과 AI에 맡긴 부분을 어떻게 나눴는가
- 생성된 코드를 어떻게 검증했는가
- 막혔을 때 어떻게 접근을 바꿨는가

"AI로 만들었다"가 아니라 **"무엇을 맡기고 무엇을 직접 판단했는가"** 를 쓰는 것이 핵심입니다.

### 결과

[ ] 반복 작업이 얼마나 줄었는지. 범위로 써도 됩니다. ("납품본 1건을 만드는 데 들던 작업이 OO에서 OO으로")

:::note
이 파이프라인의 코드는 회사 자산이라 공개하지 않습니다. 구조와 설계 판단은 설명할 수 있습니다.
:::

## docs-as-code 환경

[ ] 일상 작업 환경을 짧게. 아래는 사실에 맞게 다듬어 쓰십시오.

- Markdown 기반 문서 작성
- Git / GitHub으로 버전 관리와 리뷰
- [ ] 리뷰를 어떤 방식으로 주고받는지 (PR 리뷰 등)

이 사이트 자체가 같은 환경에서 만들어졌습니다. Docusaurus로 작성하고, GitHub Actions로 빌드·배포하며, 깨진 링크가 있으면 빌드가 실패하도록 설정해 두었습니다. 저장소는 [여기](https://github.com/schoi28/portfolio)에서 볼 수 있습니다.
