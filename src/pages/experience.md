# 실무 경험

자율주행 소프트웨어 회사에서 영문·국문 기술 문서를 담당하고 있습니다. 문서가 없거나 흩어져 있던 세 제품을 하나의 솔루션 문서 세트로 묶고, 그 문서를 만들고 검수하는 도구를 직접 개발했습니다.

:::note
실무 산출물은 대외비라 문서 자체를 공개할 수 없습니다. 이 페이지는 **무엇을 판단하고 어떻게 만들었는지**를 기록한 것입니다. 같은 구조의 문서 세트를 가상 제품으로 재현해 [Work](/work)에 공개했습니다.
:::

## 0 → 1: 통합 솔루션 문서 세트 구축

### 상황

세 제품이 하나의 솔루션으로 판매되는데, 문서는 그 형태로 존재하지 않았습니다.

| 제품 | 기존 문서 상태 |
| --- | --- |
| 라이다 인지 엔진 | 개발자가 작성한 Google Docs 사용자 매뉴얼. 코멘트가 한눈에 보이지 않아 리뷰가 정체되어 있었습니다 |
| 플릿 관리 애플리케이션 | 없음. 입사 후 개발이 시작된 제품이라 UI 요소의 이름부터 정해야 했습니다 |
| 모션 플래닝 소프트웨어 | 클라이언트에게 전달하던 5페이지 내외의 비공식 퀵 가이드만 있었습니다 |
| 솔루션 전체 | 세 제품을 묶어 설명하는 문서는 없었습니다 |

### 한 일

**라이다 인지 엔진** — 포맷을 Markdown으로 전환하고, 리뷰를 GitHub Pull Request에서 받는 구조로 바꿨습니다. SDK 문서와 API 문서까지 범위에 포함했습니다.

**플릿 관리 애플리케이션** — 정보 구조 설계부터 시작해 전체를 집필했습니다. 기획 회의에 참여해 UI 네이밍에도 관여했습니다. 운영자가 구역과 차량, 시스템 상태를 모니터링하는 제품이라 단계별 절차 가이드와 이미지 작업의 비중이 컸습니다.

**모션 플래닝 소프트웨어** — 세 제품 중 기술적 깊이가 가장 깊었습니다. 이 문서를 쓰면서 용어집 정책을 만들고, 이후 모든 매뉴얼의 공통 정책으로 적용했습니다.

**솔루션 매뉴얼** — 세 제품을 묶어 솔루션 전체를 설명하는 문서를 새로 썼습니다. 솔루션의 강점을 중심으로 개략적인 이해를 돕는 부분과, 운영자 전용 트러블슈팅 가이드를 담당했습니다.

최종적으로 **솔루션 매뉴얼과 제품별 매뉴얼을 묶은 통합 문서 세트**를 웹과 PDF 두 포맷으로 완성했습니다.

### 판단한 것들

문서를 쓰기 전에 정해야 했던 것들입니다. 이 결정들이 결과물의 모양을 정했습니다.

#### 하나로 묶을 것인가, 세 개로 둘 것인가

[확인] 어느 쪽을 선택했고 왜 그랬는지 2~3줄. 결과물이 "솔루션 매뉴얼 + 제품별 매뉴얼"의 2층 구조였으니, 아마 **둘 다 선택한 것**에 가깝습니다. 그렇다면 그 판단의 근거를 쓰면 됩니다. 예를 들어 제품을 개별 도입하는 고객과 솔루션을 통째로 도입하는 고객이 모두 있었다면, 그것이 2층 구조를 선택한 이유가 됩니다.

#### 독자를 어떻게 나눌 것인가

세 제품의 독자가 같지 않았습니다.

[확인] 독자를 몇 개 유형으로 정의했는지와 그 기준. 이미 단서가 있습니다. 모션 플래닝은 기술 깊이가 깊은 독자, 플릿 관리 애플리케이션은 운영자, 솔루션 매뉴얼의 앞부분은 도입을 검토하는 사람이었습니다. 이 셋을 유형으로 정리하면 됩니다.

독자 정의가 먼저 끝나야 같은 기능을 어느 깊이로 설명할지 정할 수 있었습니다. 이 판단 방식을 정리한 것이 [How I work](/how-i-work)이고, 가상 제품에 적용한 결과가 [Work](/work)의 네 문서 세트입니다.

#### 웹과 PDF를 어떻게 함께 유지할 것인가

두 포맷이 모두 필요했습니다. [확인] 각각 왜 필요했는지 1줄씩. 예를 들어 웹은 검색과 갱신, PDF는 납품과 오프라인 열람이었다면 그렇게 쓰면 됩니다.

두 포맷을 따로 관리하면 반드시 어긋납니다. 단일 소스에서 두 포맷을 생성하는 구조를 선택했습니다.

### 결과

[확인] 이 페이지에서 가장 중요한 칸입니다. 숫자가 없어도 되지만 **누가 무엇을 덜 하게 되었는지**는 드러나야 합니다. 아래 축 중에서 사실인 것만 고르십시오.

- 정체되어 있던 리뷰가 어떻게 바뀌었는지 (Google Docs → PR 전환의 효과)
- 제품별로 흩어져 있던 정보를 한 곳에서 확인할 수 있게 된 것
- 납품본을 만드는 데 들던 작업이 줄어든 정도
- 반복 문의가 줄어든 유형
- 신규 입사자나 신규 클라이언트의 온보딩에 걸리는 시간

## 문서 품질 기준 수립

문서를 쓰는 것과 별개로, **좋은 문서의 조건을 기준으로 만들어 전체에 적용**했습니다.

### 세 가지 절대 원칙

제품과 작성자가 달라도 지키도록 정한 규칙입니다.

1. **미리 정의한 독자 수준에 맞지 않는 용어는 예외 없이 용어집에 넣는다.** 기술 깊이가 가장 깊은 모션 플래닝 문서를 쓰면서 이 정책을 만들고, 이후 모든 매뉴얼의 공통 정책으로 적용했습니다.
2. **개념과 절차를 섞지 않는다.** 불가피한 경우를 제외하고 분리합니다.
3. **목적에 따라 바로 찾아갈 수 있도록 목차를 구성한다.** 제품 기능 순서가 아니라 독자의 목적 순서로 배열합니다.

### 국제 표준에 맞춘 구조 재정비

전체 매뉴얼의 구조를 소프트웨어 사용자 문서 국제 표준에 맞게 재정비했습니다.

[확인] 어떤 표준을 참조했는지 확인이 필요합니다. 소프트웨어 사용자 문서 관련 표준은 **ISO/IEC/IEEE 26514**(사용자 정보의 설계와 개발), **26511**(관리), **26515**(애자일 환경), **IEC/IEEE 82079-1**(사용 설명서 작성) 등이 있습니다.

:::warning
번호를 확신할 수 없다면 **번호를 쓰지 마십시오.** "소프트웨어 사용자 문서 국제 표준을 참조해 구조를 재정비했습니다"로 충분합니다. 면접에서 설명하지 못할 표준 번호를 적는 것이 번호를 생략하는 것보다 위험합니다.
:::

## 문서 빌드·검수 도구 직접 개발

처음에는 공개 정적 사이트 생성기(MkDocs)를 쓰려 했습니다. 커스터마이징할 항목이 계속 늘어나 결국 **자체 개발로 전환**했습니다.

### 만든 기능

| 기능 | 해결한 문제 |
| --- | --- |
| 웹·PDF 동시 빌드·배포 | 두 포맷을 따로 관리하면 내용이 어긋납니다. 단일 소스에서 생성합니다 |
| 브랜드 가이드라인 적용 | 회사 디자인 기준을 빌드 단계에서 일괄 적용합니다 |
| **클라이언트별 피처 플래그** | Markdown에 커스텀 주석 형식의 마크를 정의해, 특정 클라이언트 전용 기능과 그 설명이 다른 클라이언트의 산출물에 노출되지 않도록 차단합니다 |
| 검수 체커 | 반복되는 수동 점검을 자동화했습니다 |
| 레퍼런스 자동 갱신 | REST API 스키마, 설정값 목록 등 정해진 형식의 섹션을 자동으로 갱신합니다 |

### 피처 플래그가 해결한 것

클라이언트마다 제공되는 기능이 달랐습니다. 같은 소스로 여러 산출물을 만들면서, **어떤 클라이언트의 문서에 어떤 내용이 들어가는지를 사람이 기억하는 방식**은 유지되지 않습니다. 빠뜨리면 기능을 모르고, 잘못 넣으면 다른 고객의 정보가 노출됩니다.

그래서 노출 범위를 문서 안에 선언하고 빌드가 판단하도록 바꿨습니다. 사람의 기억이 아니라 구조가 보장합니다.

### 레퍼런스 자동 갱신이 해결한 것

API 스키마와 설정값 목록은 손으로 유지하면 반드시 실제 제품과 어긋납니다. 정확하게 쓰려고 노력하는 것보다 **틀릴 수 없는 구조를 만드는 쪽**이 확실하다고 판단했습니다.

### AI를 어떻게 썼는가

[확인] JD가 "AI를 활용한 문서화 경험이 있다면 구체적으로 적어주세요"라고 명시한 항목입니다. 이 페이지에서 두 번째로 중요한 칸입니다.

쓸 내용은 "AI로 만들었다"가 아니라 **무엇을 맡기고 무엇을 직접 판단했는가**입니다.

- 내가 설계한 부분 — 어떤 기능이 필요한지, 피처 플래그를 어떤 문법으로 할지, 검수 체커가 무엇을 잡아야 하는지
- AI에 맡긴 부분 — 구현, 파싱 로직, 빌드 스크립트 등
- 생성된 코드를 어떻게 검증했는지
- 막혔을 때 접근을 어떻게 바꿨는지 (MkDocs에서 자체 개발로 전환한 판단도 여기에 해당합니다)

### 결과

[확인] 반복 작업이 얼마나 줄었는지. 범위로 써도 됩니다. 예: "납품본 1건을 만드는 데 들던 작업이 [ ]에서 [ ]으로 줄었습니다."

:::note
이 도구의 코드는 회사 자산이라 공개하지 않습니다. 구조와 설계 판단은 설명할 수 있습니다.
:::

## docs-as-code 전환

가장 먼저 한 일은 포맷과 리뷰 경로를 바꾸는 것이었습니다.

기존 매뉴얼은 Google Docs에 있었고, 코멘트가 한눈에 보이지 않아 리뷰가 정체되어 있었습니다. 문서를 Markdown으로 옮기고 리뷰를 **GitHub Pull Request**에서 받도록 바꿨습니다. 개발자가 이미 매일 쓰는 도구 안으로 문서 리뷰를 옮긴 것입니다.

[확인] 전환 후 리뷰가 어떻게 달라졌는지 1~2줄. 이것이 "문서화 프로세스를 팀 워크플로에 접목한 경험"의 증거입니다.

현재 일상 작업 환경입니다.

- Markdown 기반 문서 작성
- Git · GitHub으로 버전 관리와 리뷰
- Pull Request 리뷰로 개발자·기획자 피드백 수렴

이 사이트도 같은 환경에서 만들었습니다. Docusaurus로 작성하고 GitHub Actions로 빌드·배포하며, 깨진 링크가 있으면 빌드가 실패하도록 설정했습니다. 저장소는 [여기](https://github.com/schoi28/portfolio)에서 볼 수 있습니다.
