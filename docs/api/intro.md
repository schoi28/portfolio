# VELA Vehicle API

차량 데이터를 조회하고 원격 명령을 보내는 REST API입니다. 이 문서는 VELA 플랫폼을 자사 시스템에 연동하려는 개발자를 대상으로 합니다.

:::note
이 문서는 포트폴리오용으로 창작한 가상 제품의 문서입니다. 실재하는 제품이나 조직과 관련이 없습니다.
:::

VELA는 완성차 회사(OEM)에 차량 소프트웨어 플랫폼을 공급하는 Tier 1 공급사입니다. 이 API는 VELA Cloud가 노출하는 인터페이스로, OEM의 자체 시스템과 VELA Drive(참고용 레퍼런스 앱)가 동일하게 사용합니다. VELA가 만들지 않는 것과의 경계는 [아키텍처 개요](#아키텍처-상의-위치)에서 다룹니다.

```
https://api.vela.example.com/v1
```

## 리소스 모델

다른 문서에서 부르는 이름과 API 리소스는 다음과 같이 대응합니다.

| API 리소스 | 운영 콘솔 용어 | 앱 화면 표현 | 설명 |
| --- | --- | --- | --- |
| `vehicle` | 차량 | 내 차량 | 등록된 차량 한 대 |
| `signal` | 시그널 | (노출 안 함) | 차량이 보고하는 데이터 항목 |
| `command` | 원격 명령 | 빠른 제어 | 차량에 보내는 지시 |
| `campaign` | 캠페인 | 소프트웨어 업데이트 | 배포 단위 |
| `sensor` | 센서 | (노출 안 함) | VELA Sense로 장착된 센서 모듈 |
| `zone` | 존 | (노출 안 함) | 차량 내 물리적 구역 (전방·후방·좌측·우측) |

같은 개념에 세 개의 이름이 존재한다는 사실을 숨기지 않고 대응표로 드러냅니다. 개발자가 고객사 담당자와 대화할 때 용어가 어긋나는 문제를 줄이기 위해서입니다.

## 아키텍처 상의 위치

```
VELA Drive / OEM 시스템 / 서드파티 연동
              │  REST (본 API)
        VELA Cloud
              │  셀룰러 연결 (mTLS)
     차량의 중앙 연산 장치 (CCU)
        VELA OS 구동
              │  자동차용 이더넷
       존 ECU ── VELA Sense
```

이 API는 VELA Cloud와 그 위의 애플리케이션 사이의 경계입니다. CCU 이하의 차량 내부 통신(존 ECU, VELA Sense와의 통신)은 이 API의 범위 밖이며, VELA OS가 처리합니다.

## 환경

| 환경 | 기본 URL | 용도 |
| --- | --- | --- |
| 스테이징 | `https://api.staging.vela.example.com/v1` | 통합 개발과 테스트. 실제 차량과 연결되지 않고 시뮬레이션된 차량 데이터를 반환합니다 |
| 프로덕션 | `https://api.vela.example.com/v1` | 실제 차량과 통신합니다 |

스테이징 환경의 시뮬레이션 차량은 `vehicle_id`가 `sim_`으로 시작합니다. 원격 명령을 보내면 2초의 지연 후 항상 성공 응답을 반환하며, 사전 조건 검사는 건너뜁니다.

## 버전 정책

- API 버전은 URL 경로(`/v1`)로 표시합니다.
- 하위 호환을 깨는 변경(필드 제거, 타입 변경, 필수 파라미터 추가)이 있을 때만 버전을 올립니다. 필드 추가는 버전을 올리지 않습니다.
- 이전 버전은 새 버전 출시 후 **최소 18개월** 지원합니다. 지원 종료 6개월 전에 등록된 이메일로 안내합니다.
- 지원 종료 일정은 [레퍼런스 · 변경 이력](./reference.md#변경-이력)에서 확인할 수 있습니다.

## 설계 노트

> 이 문서를 왜 이렇게 설계했는지에 대한 기록입니다.

**독자**: 연동을 담당하는 개발자. REST와 OAuth는 알지만 VELA 제품은 처음이라고 가정했습니다. 순서대로 읽지 않고 필요한 항목만 검색해서 봅니다.

**구조 결정**: 엔드포인트 목록보다 리소스 모델 표를 앞에 뒀습니다. 개발자가 가장 먼저 알아야 하는 것은 "이 제품의 데이터 모델이 어떻게 생겼는가"입니다. 리소스 모델 바로 다음에 아키텍처 다이어그램을 넣은 것도 같은 이유입니다 — 이 API가 시스템 전체에서 어디를 담당하는지 알아야 나머지 장의 범위가 이해됩니다.

**용어 대응표를 넣은 이유**: 이 API의 사용자는 완성차 회사와 협력사 개발자입니다. 이들은 운영자·사용자와 같은 대상을 다른 이름으로 부릅니다. 표를 한 번 제공하면 이후 문서 전체에서 번역 부담이 사라집니다.

**시그널 카탈로그를 스펙에서 생성하는 이유**: 4장의 시그널 표는 손으로 유지하면 반드시 실제 API와 어긋납니다. OpenAPI 스펙 한 곳에서 문서를 생성해 어긋날 여지를 없앨 계획입니다. 문서를 정확하게 쓰는 것보다 **틀릴 수 없는 구조를 만드는 쪽**이 확실합니다.

**스테이징 환경 동작을 문서화한 이유**: "테스트 환경은 이렇게 다릅니다"를 명시하지 않으면 개발자가 프로덕션에서야 사전 조건 실패를 처음 겪습니다. 실패를 미리 알려주는 것이 questions 수를 줄이는 가장 큰 요인이라는 원칙을 API 문서에도 동일하게 적용했습니다.
