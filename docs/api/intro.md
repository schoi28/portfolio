# VELA Vehicle API

## 이 문서에 대해

VELA Cloud가 외부에 노출하는 REST API와 SDK의 레퍼런스입니다. 차량 데이터를 조회하고, 원격 명령을 보내고, 소프트웨어 배포를 제어하는 방법을 다룹니다.

| 구분 | 내용 |
| --- | --- |
| 다루는 것 | 인증 · 차량 데이터 조회 · 원격 명령 · 센서 상태 · OTA 캠페인 · 웹훅 · 에러 처리 |
| 다루지 않는 것 | 차량 내부 통신(존 ECU, VELA OS 내부 API) · 운영 콘솔의 화면 조작(→ [VELA Deploy](../deploy/intro.md)) · 센서 장착(→ [VELA Sense](../sensor/intro.md)) |
| API 버전 | `v1` |
| 기본 URL | `https://api.vela.example.com/v1` |

## 대상 독자

VELA 플랫폼을 자사 시스템에 연동하는 개발자를 기준으로 썼습니다. **REST와 OAuth 2.0은 알고 있다고 전제하지만, VELA 제품은 처음이라고 가정합니다.**

| 역할 | 하는 일 | 먼저 읽을 곳 |
| --- | --- | --- |
| **OEM 애플리케이션 개발자** | 자사 브랜드 앱에서 차량 데이터를 쓴다 | [VELA Vehicle API란](./overview.md) → [빠르게 시작하기](./quickstart.md) → [차량 데이터 조회하기](./vehicle-data.md) |
| **협력사 개발자** | VELA 플랫폼 위에서 기능을 개발한다 | [원격 명령 보내기](./remote-commands.md) · [웹훅으로 이벤트 받기](./webhooks.md) |
| **릴리스 자동화 담당자** | 배포를 콘솔이 아니라 코드로 수행한다 | [OTA 배포 제어하기](./ota.md) · [VELA Deploy 운영 가이드](../deploy/intro.md) |
| **검증 엔지니어** | 개발 차량의 센서 상태를 확인한다 | [센서 상태 조회하기](./sensors.md) · [VELA Sense 설치 가이드](../sensor/intro.md) |

전제하는 지식은 다음과 같습니다.

- HTTP 메서드와 상태 코드, JSON 읽고 쓰기
- OAuth 2.0 클라이언트 자격 증명 흐름
- 비동기 처리(폴링 또는 웹훅 수신)를 구현할 수 있을 것

**자율주행이나 차량 전장 구조에 대한 사전 지식은 전제하지 않습니다.** 필요한 개념은 [VELA Vehicle API란](./overview.md)와 [용어 찾아보기](./glossary.md)에서 설명합니다.

## 표기 규약

### 안내 상자

| 등급 | 이 문서에서 쓰는 경우 |
| --- | --- |
| **경고** | 자격 증명 유출, 되돌릴 수 없는 명령, 중대한 피해로 이어지는 경우 |
| **주의** | 토큰 만료, 중복 이벤트, 복구 가능한 오류 |
| **참고** | 알아 두면 구현이 수월해지는 정보 |

이 문서에는 **'위험' 등급이 나오지 않습니다.** 신체 위험이 없기 때문입니다. 전체 정의는 [표기 규약](../#표기-규약)에 있습니다.

### 글자 표기

| 표기 | 뜻 |
| --- | --- |
| `GET /vehicles` | 메서드와 경로 |
| `vehicle_id` | 파라미터·필드 이름 |
| `{vehicle_id}` | 값을 바꿔 넣는 자리 |
| **굵은 글씨** | 콘솔 화면에 표시된 요소의 이름 |

모든 예시 요청은 `curl`로 적고, 같은 동작을 Python SDK로도 보여 줍니다.

## 설계 노트

> 이 문서를 왜 이렇게 설계했는지에 대한 기록입니다. 실제 제품 문서에는 포함되지 않습니다.

**독자**: 연동을 담당하는 개발자. REST와 OAuth는 알지만 VELA 제품은 처음이라고 가정했습니다. 순서대로 읽지 않고 필요한 항목만 검색해서 봅니다.

**구조 결정**: 엔드포인트 목록보다 리소스 모델 표를 앞에 뒀습니다. 개발자가 가장 먼저 알아야 하는 것은 "이 제품의 데이터 모델이 어떻게 생겼는가"입니다. 리소스 모델 바로 다음에 아키텍처 다이어그램을 넣은 것도 같은 이유입니다. 이 API가 시스템 전체에서 어디를 담당하는지 알아야 나머지 장의 범위가 이해됩니다.

**머리말과 1장을 나눈 이유**: 검색으로 들어온 개발자는 머리말을 읽지 않습니다. 그래서 **문서를 읽는 방법**(독자 정의, 표기 규약)과 **제품을 이해하는 데 필요한 내용**(리소스 모델, 아키텍처)을 분리했습니다. 후자는 어느 장에서든 되돌아와야 하는 내용이라 독립된 장이어야 합니다.

**정보 유형 분류**: 각 장은 리소스 하나를 다루는 절차 문서이고, 조회해야 하는 값은 전부 [레퍼런스 찾아보기](./reference.md)에 모았습니다. 시그널 카탈로그를 차량 데이터 장에서 레퍼런스로 옮긴 것이 그 예입니다. 개발자는 "어떻게 가져오는가"와 "어떤 값이 있는가"를 다른 시점에 찾습니다. 전자는 처음 한 번, 후자는 작업 중 계속입니다. 두 가지를 한 장에 두면 긴 표가 절차를 끊습니다.

**용어 대응표를 넣은 이유**: 이 API의 사용자는 완성차 회사와 협력사 개발자입니다. 이들은 운영자·사용자와 같은 대상을 다른 이름으로 부릅니다. 표를 한 번 제공하면 이후 문서 전체에서 번역 부담이 사라집니다.

**용어집을 API 용어가 아니라 도메인 용어로 채운 이유**: `vehicle_id`가 무엇인지는 레퍼런스가 설명합니다. 개발자가 막히는 지점은 그게 아니라 **CCU, 존 ECU, OTA 캠페인 같은 차량 도메인 용어**입니다. 웹 개발 경력만 있는 주니어 개발자를 기준으로 용어집을 채웠습니다.

**시그널 카탈로그를 스펙에서 생성하는 이유**: 레퍼런스의 시그널 표는 손으로 유지하면 반드시 실제 API와 어긋납니다. OpenAPI 스펙 한 곳에서 문서를 생성해 어긋날 여지를 없앨 계획입니다. 문서를 정확하게 쓰는 것보다 **틀릴 수 없는 구조를 만드는 쪽**이 확실합니다.

**스테이징 환경 동작을 문서화한 이유**: "스테이징 환경은 이렇게 다릅니다"를 명시하지 않으면 개발자가 프로덕션에서야 사전 조건 실패를 처음 겪습니다. 실패를 미리 알려 주는 것이 문의 수를 줄이는 가장 큰 요인이라는 원칙을 API 문서에도 동일하게 적용했습니다.
