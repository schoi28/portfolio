# VELA Deploy 운영 가이드

## 이 문서에 대해

VELA Deploy는 차량 소프트웨어를 단계적으로 배포하고, 문제가 생기면 되돌리는 운영 콘솔입니다. 이 문서는 캠페인을 만들고 운영하고 종료하기까지의 전 과정을 다룹니다.

| 구분 | 내용 |
| --- | --- |
| 다루는 것 | 패키지 업로드 · 타깃 그룹 · 캠페인 생성 · 단계적 롤아웃 · 게이트 판정 · 롤백과 긴급 중단 · 감사 로그 |
| 다루지 않는 것 | 패키지를 만드는 빌드 과정 · 같은 작업의 API 수행(→ [VELA Vehicle API · OTA 배포 제어하기](../api/ota.md)) · 차량 쪽 설치 동작 |
| 적용 버전 | VELA Deploy 2.4 |

## 대상 독자

배포를 실제로 집행하는 릴리스 운영자를 기준으로 썼습니다. **코드를 읽을 수 있다고 전제하지 않습니다.**

| 역할 | 하는 일 | 먼저 읽을 곳 |
| --- | --- | --- |
| **릴리스 운영자** | 캠페인을 만들고 단계를 올린다 | [VELA Deploy란](./overview.md) → [첫 캠페인 만들어 보기](./first-campaign.md) |
| **릴리스 책임자** | 배포 범위를 승인하고 중단을 결정한다 | [롤아웃 운영하기](./rollout.md) · [문제에 대응하기](./incident-response.md) |
| **품질·규제 담당자** | 배포 이력을 증빙으로 제출한다 | [감사 기록 관리하기](./audit.md) |
| **자동화 담당 개발자** | 같은 작업을 API로 수행한다 | [VELA Vehicle API · OTA 배포 제어하기](../api/ota.md) |

전제하는 지식은 다음과 같습니다.

- 업무용 웹 콘솔을 다룰 수 있을 것
- 버전 번호와 릴리스 노트의 개념을 알고 있을 것
- 백분율로 표시된 비율을 읽고 판단할 수 있을 것

**차량 전장 구조나 무선 업데이트의 내부 동작은 전제하지 않습니다.** 필요한 개념은 [VELA Deploy란](./overview.md)와 [용어 찾아보기](./glossary.md)에서 설명합니다.

## 표기 규약

### 안내 상자

| 등급 | 이 문서에서의 쓰임 |
| --- | --- |
| **경고** | 긴급 중단, 롤백 불가 조건 — 되돌릴 수 없는 결정 |
| **주의** | 조건 설정 실수, 일시 중지의 범위 오해 — 복구 가능한 오류 |
| **참고** | 판단에 참고할 배경 정보 |

이 문서에는 **'위험' 등급이 나오지 않습니다.** 신체 위험이 없기 때문입니다. 다만 '경고'는 다른 세트보다 많습니다. 배포에는 되돌리기 어려운 동작이 많습니다. 전체 정의는 [표기 규약](../#표기-규약)에 있습니다.

### 글자 표기

| 표기 | 뜻 |
| --- | --- |
| **굵은 글씨** | 콘솔 화면에 표시된 요소의 이름 |
| **패키지 > 새 패키지** | 메뉴를 차례로 선택하는 경로 |
| `in_progress` | 시스템이 기록하는 상태 값. 화면에는 한국어로 표시됩니다 |

본문의 숫자 기준(성공률, 대기 시간 등)은 **예시**입니다. 조직의 위험 허용 수준에 따라 정해야 합니다.

## 설계 노트

> 이 문서를 왜 이렇게 설계했는지에 대한 기록입니다. 실제 제품 문서에는 포함되지 않습니다.

**독자**: 릴리스 운영자. 업무 도구에는 익숙하지만 코드는 읽지 못합니다. 평소에는 절차대로 진행하고, 사고가 났을 때 급히 찾아봅니다.

**구조 결정**: 개념을 1장에 모으고 절차와 섞지 않았습니다. 배포 도구의 문서가 어려워지는 가장 흔한 이유는 절차 중간에 개념 설명이 끼어들기 때문입니다. 개념을 먼저 한 번 정리하면 이후 절차가 짧아집니다.

**머리말과 1장을 나눈 이유**: 머리말은 **이 문서를 읽을 사람인지 판단하는 데** 쓰이고, 1장은 **일을 하는 데** 쓰입니다. 운영자는 사고가 났을 때 상태 값의 의미를 다시 확인하러 1장으로 돌아옵니다. 머리말에는 돌아오지 않습니다.

**정보 유형 분류**: 네 세트 중 유형이 가장 깨끗하게 나뉜 문서입니다. 개념은 1장, 절차는 2~6장, 조회용 값은 [레퍼런스 찾아보기](./reference.md)에 있습니다. 가능했던 이유는 장의 배열 축이 **캠페인의 생애주기**라서입니다. 시간 순서로 배열하면 개념이 끼어들 자리가 없습니다. 정렬 축을 고르는 순간 유형 분리의 난이도가 결정됩니다.

**문제 대응 장을 독립적으로 쓰는 이유**: 사고가 났을 때 사람은 문서를 처음부터 읽지 않습니다. 문제 대응 장은 앞 장을 읽지 않아도 이해되도록 필요한 개념을 그 자리에서 다시 설명합니다. 다른 장에서는 피하는 중복을 여기서만 의도적으로 허용합니다.

**판단 기준을 표로 쓰는 이유**: "오류율이 높으면 중단합니다" 같은 서술은 급할 때 읽히지 않습니다. 숫자와 조치를 표로 제시합니다. 다만 숫자는 조직마다 다르므로 예시임을 명시합니다.

**용어집을 따로 둔 이유**: 이 문서의 독자는 코드를 읽지 못하지만 `in_progress` 같은 상태 값은 로그에서 마주칩니다. 상태 값은 [레퍼런스 찾아보기](./reference.md)에, 개념어는 [용어 찾아보기](./glossary.md)에 나눠 두었습니다. 찾는 시점이 다르기 때문입니다.
