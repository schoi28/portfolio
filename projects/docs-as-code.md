# 문서 운영 체계 수립과 docs-as-code 전환

> 자율주행 솔루션 소프트웨어 회사 · Technical Writer · 2025.01 ~ 현재

**사람의 기억과 개별 판단에 의존하던 문서 운영 방식을, 팀이 함께 사용할 수 있는 기준과 리뷰 워크플로로 바꿨습니다. 문서 저장소를 운영하는 방법과 실제 콘텐츠를 판단하는 기준을 각각 문서화하고, Google Docs 중심의 리뷰를 GitHub Pull Request 기반으로 전환했습니다.**

## 어려웠던 점

**문서의 품질과 범위를 판단하는 기준이 사람마다 달랐습니다.**

제품과 문서가 늘어나면서 단순히 문장을 어떻게 쓸 것인지보다 더 근본적인 판단이 필요해졌습니다.

예를 들어 다음과 같은 질문에는 명확한 기준이 필요했습니다.

- 이 내용은 사용자 매뉴얼에 들어가야 하는가
- 본문에서 설명해야 하는가, 부록으로 보내야 하는가
- 개발자에게 필요한 정보와 일반 사용자에게 필요한 정보를 어디까지 구분해야 하는가
- 내부 구현 정보가 사용자 문서에 들어가도 되는가
- 설정값을 본문에서 설명해야 하는가, 별도 레퍼런스로 분리해야 하는가
- 새로운 기능을 기존 문서에 추가할지 별도 페이지로 만들지 어떻게 결정할 것인가

이런 판단이 정리되어 있지 않으면 리뷰할 때마다 같은 논의를 반복하게 됩니다.

누군가는 “중요한 정보이니 본문에 넣자”고 하고, 다른 사람은 “너무 기술적이니 제외하자”고 할 수 있습니다. 판단 근거가 없으면 결국 개인의 의견 대 개인의 의견이 됩니다.

**문서 저장소를 운영하는 방법도 별도로 정리할 필요가 있었습니다.**

제품과 버전이 늘어나면서 새 제품이나 릴리스, 기능을 문서 시스템에 추가하는 방법도 복잡해졌습니다.

작성자는 다음과 같은 구조를 이해해야 했습니다.

- 새 제품과 버전을 어디에 추가하는가
- 내비게이션 구조를 어떻게 설정하는가
- 조건부 콘텐츠는 어떤 마커로 관리하는가
- 이미지와 파일은 어디에 배치하는가
- 용어집과 툴팁은 어떻게 연결하는가

이는 콘텐츠의 옳고 그름을 판단하는 문제와는 성격이 달랐습니다.

**문서 리뷰도 장기간 멈추는 경우가 있었습니다.**

기존 매뉴얼은 Google Docs에서 리뷰했습니다.

코멘트가 문서 곳곳에 흩어져 있어 어떤 부분에 검토가 필요한지 한눈에 파악하기 어려웠고, 누가 어떤 의견을 남겼는지 추적하기도 쉽지 않았습니다.

기능 담당자에게 별도로 리뷰를 요청해야 했기 때문에 요청 시점과 담당자에 따라 검토가 몇 주씩 지연되기도 했습니다.

문서 자체보다 **리뷰를 요청하고 추적하는 과정이 병목**이 되고 있었습니다.

## 해결 방법

### 작성 원칙 줄이기

모든 상황을 세부 규칙으로 만들기보다, 제품이 달라져도 공통으로 적용할 수 있는 원칙부터 정했습니다.

핵심 원칙은 세 가지로 줄였습니다.

1. 미리 정의한 독자의 사전 지식 수준을 벗어나는 용어는 **예외 없이 용어집에서 설명하기**
2. **개념과 절차를 구분하기**
3. 제품 기능 순서가 아니라 **독자가 하려는 일의 순서로 정보 구성하기**

규칙을 많이 만드는 것보다 실제 문서를 작성하고 검토할 때 반복해서 적용할 수 있는 기준을 만드는 것이 중요하다고 판단했습니다.

전체 매뉴얼의 구조를 정비할 때는 사용 설명서 작성에 관한 국제 표준인 **IEC/IEEE 82079-1**도 참고했습니다.

표준을 그대로 적용하기보다 현재 제품과 독자에게 필요한 구조를 검토하는 기준으로 사용했습니다.

### 문서 구성 방법 정리하기

먼저 **문서 시스템을 어떻게 구성하고 사용하는지**를 별도의 가이드로 정리했습니다.

이 가이드는 콘텐츠 자체를 어떻게 판단할지보다, Markdown 기반 문서 저장소와 빌드 환경을 일관된 방식으로 운영하기 위한 문서입니다.

| 가이드 | 주요 내용 |
| --- | --- |
| 설정 가이드 | 새 버전·제품·솔루션·기능 추가 방법, 내비게이션 구성, 조건부 콘텐츠 설정 |
| 작성 가이드 | Markdown 문법, 이미지 처리, 용어집 툴팁 적용, 파일과 디렉터리 구성 |

가이드는 기능 목록을 나열하기보다 **작성자가 무엇을 하려는지**를 기준으로 구성했습니다.

예를 들어 설정값을 하나씩 설명하기보다 다음과 같은 작업에서 출발하도록 했습니다.

- 새 제품 추가하기
- 새 버전 추가하기
- 솔루션에 제품 연결하기
- 특정 기능을 조건부 콘텐츠로 관리하기
- 새 문서를 내비게이션에 연결하기

제품 매뉴얼에서 사용한 **독자의 목적 중심 정보 구조**를 내부 작성 가이드에도 동일하게 적용했습니다.

### 콘텐츠 판단 기준 만들기

문서 저장소를 사용하는 방법과 별개로, **실제 매뉴얼에 무엇을 넣고 어떻게 배치할지를 판단하는 기준**도 필요했습니다.

이를 위해 Confluence에 **Technical Writing Guide**를 작성해 팀 내부의 공통 기준으로 사용했습니다.

이 가이드의 목적은 문체를 통일하는 데만 있지 않았습니다. 리뷰 과정에서 테크니컬 라이터와 유관 부서가 다음과 같은 질문에 같은 기준으로 답할 수 있도록 하는 것이 더 중요했습니다.

- 어떤 정보가 사용자 매뉴얼의 범위에 포함되는가
- 어떤 정보는 매뉴얼에 포함하지 않는가
- 핵심 사용 흐름에 필요한 내용과 참고용 정보를 어떻게 구분하는가
- 어떤 내용은 본문에 두고 어떤 내용은 부록이나 레퍼런스로 분리하는가
- 내부 구현 설명과 사용자가 알아야 할 기술 정보를 어떻게 구분하는가
- 특정 역할에만 필요한 정보를 전체 독자에게 노출해야 하는가
- 상세 설정값을 본문에서 설명할지 별도 참조 문서로 분리할지 어떻게 판단하는가

핵심은 **“이 정보가 중요하냐”가 아니라 “이 독자가 자신의 목적을 달성하는 데 필요한 정보인가”를 기준으로 판단하는 것**이었습니다.

예를 들어 기술적으로 중요한 정보라도 사용자가 제품을 설치하거나 운영하고 문제를 해결하는 데 필요하지 않다면 사용자 매뉴얼의 본문에 넣지 않을 수 있습니다.

반대로 세부 기술 정보라도 특정 독자가 작업을 완료하기 위해 반드시 알아야 한다면 해당 독자를 위한 문서나 레퍼런스에 포함해야 합니다.

이 기준을 통해 `본문 / 부록 / 별도 레퍼런스 / 문서 범위 밖`을 구분할 수 있도록 했습니다.

### 리뷰 판단의 근거 공유하기

Technical Writing Guide는 실제 리뷰에서도 판단 근거로 사용했습니다.

문서 작성자와 기능 담당자의 관점은 다를 수 있습니다.

기능 담당자는 자신이 개발한 기능의 세부 사항을 최대한 많이 전달하고 싶어 할 수 있고, 테크니컬 라이터는 독자에게 필요한 정보만 남기려고 할 수 있습니다.

이때 단순히 “이 내용은 너무 기술적입니다”라고 말하는 대신,

- 대상 독자가 누구인지
- 그 독자가 수행해야 할 작업이 무엇인지
- 이 정보가 작업 수행에 필요한지
- 본문에 있어야 하는지 참고 정보로 분리해도 되는지

를 기준으로 논의할 수 있게 했습니다.

이를 통해 문서 범위와 구조에 관한 결정을 **개인의 취향이 아니라 공유된 원칙에 근거한 판단**으로 설명할 수 있도록 했습니다.

### 리뷰를 Pull Request로 옮기기

콘텐츠 기준을 정한 뒤에는 실제 리뷰 과정도 개발자가 이미 사용하고 있는 GitHub 워크플로 안으로 옮겼습니다.

- 문서를 Markdown 기반으로 관리하기
- 변경 사항을 Pull Request 단위로 리뷰받기
- 브랜치별로 해당 시점의 문서 버전을 추적하기
- 리뷰가 필요한 파일과 변경 부분을 diff로 바로 확인하기
- 최종 리뷰에서 확인해야 할 항목을 미리 정해 검토 범위를 명확히 하기

별도의 문서 리뷰 환경을 새로 익히게 하는 대신, 개발자가 코드 리뷰에 사용하는 방식과 최대한 비슷하게 구성했습니다.

덕분에 리뷰어는 전체 문서를 다시 읽지 않고도 **실제로 달라진 부분부터 확인**할 수 있게 됐습니다.

### 리뷰 요청 작게 나누기

한 번에 큰 문서를 검토받는 대신 변경 단위를 작게 유지했습니다.

소규모 업데이트라도 필요한 시점에 Pull Request를 만들고, 변경된 기능과 관련된 담당자에게 해당 부분만 검토를 요청했습니다.

이 방식은 리뷰 요청 횟수 자체는 늘리지만, 한 번에 검토해야 할 범위를 줄입니다.

또한 변경 사항이 생긴 시점과 리뷰 시점의 간격을 줄여, 기능 담당자가 당시의 맥락을 기억하고 있을 때 피드백을 받을 수 있었습니다.

## 결과

- 문서 시스템을 운영하는 방법과 실제 콘텐츠를 판단하는 기준을 분리해 **작성자가 무엇을 어떻게 결정해야 하는지 명확하게 했습니다.**
- Confluence의 Technical Writing Guide를 통해 본문·부록·레퍼런스·문서 범위 밖 콘텐츠를 구분할 수 있는 **공통 판단 기준을 마련했습니다.**
- 문서 범위와 정보 배치에 관한 리뷰에서 개인의 선호 대신 **독자와 목적을 기준으로 논의할 수 있는 근거**를 만들었습니다.
- 몇 주씩 지연되던 경우가 있던 문서 리뷰가 전환 후에는 **대부분 1~2일 안에 완료**됐습니다.
- Pull Request의 diff를 통해 변경된 부분을 바로 확인할 수 있어 **비교와 검토가 직관적이라는 피드백**을 받았습니다.
- 작성 원칙과 운영 가이드를 문서로 남겨 제품이나 작성자가 달라져도 **같은 기준을 반복해서 적용할 수 있는 기반**을 마련했습니다.
- 문서 작업을 기존 개발 워크플로 안으로 옮겨 기능 담당자가 별도의 리뷰 도구를 사용하지 않고도 문서 검토에 참여할 수 있게 했습니다.
