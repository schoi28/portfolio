# 통합 솔루션 문서 세트 신규 구축

## 어려웠던 점

**제품은 하나의 솔루션으로 판매되지만, 문서는 제품별로도 필요했습니다.**

회사는 여러 자율주행 소프트웨어 제품을 하나의 솔루션으로 묶어 기업 고객에게 판매합니다. 그러나 고객사마다 구매하는 제품 구성이 다르고, 일부 제품은 솔루션과 별개로 단독 판매되기도 합니다.

솔루션 단위의 문서만 만들면 일부 제품만 구매한 고객에게 불필요한 정보가 함께 제공됩니다. 반대로 제품별 문서만 만들면 여러 제품이 결합해 어떤 솔루션을 구성하는지 설명할 수 없습니다.

따라서 문서 구조가 제품 자체뿐 아니라 **판매 방식과 고객의 사용 방식까지 함께 반영해야 했습니다.**

**제품마다 문서화의 출발점도 달랐습니다.**

| 제품 | 시작 시점의 문서 상태 |
| --- | --- |
| 라이다 인지 엔진 | 개발자가 작성한 Google Docs 매뉴얼이 있었으나 리뷰가 장기간 지연되고 있었음 |
| 운영 애플리케이션 | 기존 문서가 없었으며 제품 개발 초기부터 문서화를 시작함 |
| 모션 플래닝 소프트웨어 | 고객에게 필요할 때마다 전달하던 5페이지 분량의 비공식 가이드만 존재 |
| 솔루션 전체 | 여러 제품을 하나의 시스템으로 설명하는 문서가 없었음 |

하나의 템플릿을 모든 제품에 그대로 적용하는 방식으로는 해결하기 어려웠습니다. 제품마다 기존 자료의 수준과 독자, 기술적 깊이가 달랐기 때문입니다.

**독자가 누구인지 명확하게 정의되어 있지 않았습니다.**

기업 고객에게 납품되는 제품이어서 실제 문서를 누가 읽는지 명확하게 정리되어 있지 않았습니다. 고객사마다 조직 구조와 직무 명칭도 달랐습니다.

독자를 정의하지 않으면 어느 수준까지 설명해야 하는지, 어떤 용어에 설명이 필요한지, 어떤 내용을 같은 문서에 배치해야 하는지 결정할 기준이 없습니다.

## 해결 방법

### 판매 구조에 맞춰 문서 계층 나누기

문서를 **솔루션 매뉴얼과 제품별 사용자 매뉴얼**이라는 두 계층으로 설계했습니다.

```text
솔루션 매뉴얼
├── 비즈니스 관점의 솔루션 개요
└── 운영자를 위한 핵심 개념 · 운영 · 트러블슈팅

제품별 사용자 매뉴얼
└── 각 제품을 직접 사용하는 독자를 위한 상세 정보
```

솔루션 매뉴얼은 여러 제품이 결합해 어떤 시스템을 구성하는지 설명하고, 제품별 사용자 매뉴얼은 각 제품을 실제로 사용하는 데 필요한 상세 정보를 제공합니다.

이를 통해 전체 솔루션을 구매한 고객과 일부 제품만 사용하는 고객 모두에게 필요한 범위의 문서를 제공할 수 있도록 했습니다.

고객사별로 달라지는 제품 구성은 문서를 복제해 별도로 관리하지 않고, [문서 빌드·검수 도구](./build-tooling.md)에서 필요한 범위를 조립하도록 분리했습니다.

### 실제 프로젝트에서 독자 조사하기

독자를 내부에서 추측하는 대신 실제 고객사 프로젝트에 참여해 각 제품에 어떤 역할의 사용자가 접근하는지 확인했습니다.

고객사마다 서로 다른 직무 명칭을 그대로 사용하지 않고, 여러 프로젝트에 공통으로 적용할 수 있도록 세 가지 독자 계층으로 일반화했습니다.

| 계층 | 누구인가 | 전제하는 사전 지식 |
| --- | --- | --- |
| 이해 | 솔루션 도입을 검토하는 독자 | 없음 |
| 운영 | 관리자 · 운영자 · 조회자 · 현장 운영자 · 원격 운전자 | 일반적인 컴퓨터 활용 능력과 소프트웨어 UI 사용 경험 |
| 기술 | 현장 배포 엔지니어 · 차량 통합 엔지니어 · 개발자 · IT 관리자 | 역할에 따라 Linux 명령줄, 네트워크, 차량 컨트롤러 통합, REST API 등 |

모든 제품 문서에는 **“자율주행에 대한 사전 지식을 전제하지 않는다”**는 공통 기준을 적용했습니다.

이 기준은 이후 용어집과 설명의 깊이를 결정하는 기준으로도 사용했습니다. 어떤 용어가 독자에게 낯선지 판단하려면 먼저 독자의 사전 지식 수준이 정의되어 있어야 하기 때문입니다.

### 독자와 읽을 범위 연결하기

독자 역할을 정의하는 데서 끝내지 않고 실제 문서 탐색에도 연결했습니다.

- 역할 표에 관련 섹션을 함께 표시해 자신의 역할을 찾으면 읽어야 할 범위도 확인할 수 있도록 했습니다.
- 역할 구분은 문서를 읽기 위한 안내이며 시스템 계정 권한을 의미하지 않는다는 점을 명시했습니다.
- 고객사마다 다른 직무 명칭 대신 일반화된 역할명을 사용하고, 가장 가까운 역할을 참고하도록 안내했습니다.
- 여러 문서를 순서대로 읽어야 하는 경우에는 문서 간 선후 관계를 명시했습니다.

독자가 문서 전체를 처음부터 읽는 것이 아니라 **자신에게 필요한 정보의 시작점을 찾을 수 있도록 하는 것**을 목표로 했습니다.

### 제품별 출발점에 맞춰 문서화하기

공통 정보 구조와 독자 기준은 유지하되, 각 제품의 기존 상태에 따라 문서화 방법을 달리했습니다.

- **운영 애플리케이션:** 문서가 없는 상태에서 정보 구조부터 설계하고 전체 사용자 문서를 신규 작성했습니다. 제품 기획 과정에도 참여해 UI 요소의 명칭을 함께 정했습니다.
- **라이다 인지 엔진:** 기존 문서를 Markdown 기반 구조로 옮기고 SDK와 API 관련 내용까지 문서 범위를 확장했습니다.
- **모션 플래닝 소프트웨어:** 기술적 깊이가 가장 높은 제품을 문서화하면서 용어 설명 기준을 정립했고, 이후 다른 제품에도 같은 기준을 적용했습니다.
- **솔루션 매뉴얼:** 개별 제품 문서에서 설명할 수 없었던 솔루션 전체 구조와 핵심 개념, 운영 절차, 트러블슈팅을 새로 작성했습니다.

모든 제품을 하나의 템플릿에 맞추는 대신, **제품별 차이는 유지하면서 독자가 일관된 방식으로 정보를 탐색할 수 있도록 공통 기준을 적용했습니다.**

## 결과

- 제품별로 흩어져 있던 문서를 **솔루션과 제품이라는 하나의 정보 구조 아래에서 운영할 수 있게 됐습니다.**
- 고객사마다 제품 구성이 달라도 문서를 새로 복사하거나 손으로 조합하지 않고, 필요한 범위를 지정해 제공할 수 있게 했습니다.
- 웹 매뉴얼의 검색 기능을 통해 현장 배포 및 필드 애플리케이션 엔지니어가 필요한 정보를 빠르게 찾을 수 있다는 피드백을 받았습니다.
- 구축한 문서는 실제 업무에서 **온보딩 자료로도 활용되고 있습니다.**
- 이 프로젝트에서 정의한 독자 모델과 정보 구조 원칙은 이후 제품 문서와 문서 운영 체계를 설계하는 기준으로 이어졌습니다.
