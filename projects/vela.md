## 어려웠던 점

**서로 무관한 샘플 몇 편만으로는 문서 설계 능력을 보여 주기 어려웠습니다.**

개별 문서 몇 편만 만들면 문장이나 한 페이지의 완성도는 보여 줄 수 있습니다.

하지만 실제 제품 문서에서는 다음과 같은 요소가 함께 작동합니다.

- 같은 기능을 독자마다 얼마나 다르게 설명하는지
- 여러 문서에서 용어와 표현이 일관되는지
- 문서 사이의 역할과 연결 관계가 명확한지
- 서로 다른 문서 유형이 하나의 제품군 안에서 어떻게 구성되는지
- 문서 수가 늘어나도 같은 품질 기준을 유지할 수 있는지

따라서 단편적인 샘플이 아니라 **서로 연결된 하나의 문서 시스템**을 만들어야 했습니다.

**가상의 제품이더라도 실무와 유사한 복잡도가 필요했습니다.**

제품 구조가 너무 단순하면 정보 구조나 독자 구분, 레퍼런스 설계, 품질 검증 같은 실무 역량을 보여 주기 어렵습니다.

그래서 단순히 문서부터 작성하지 않고 먼저 차량용 소프트웨어 플랫폼 공급사 **VELA**와 네 가지 제품을 설계한 뒤, 제품 간 관계와 사용자를 정의했습니다.

문서 샘플이 아니라 **문서가 필요할 정도로 복잡한 제품 환경 자체를 먼저 만드는 것**에서 시작했습니다.

## 해결 방법

### 하나의 기능을 네 독자에게 다르게 설명하기

VELA 제품군에서 공통으로 등장하는 **무선 업데이트** 기능을 기준으로, 네 종류의 독자가 같은 기능을 어떻게 다르게 이해해야 하는지 설계했습니다.

| 문서 세트 | 독자 | 문서 유형 | 같은 기능을 어떻게 다루나 |
| --- | --- | --- | --- |
| VELA Drive 앱 사용 설명서 | 차량 소유자 | 튜토리얼 · 하우투 · FAQ | 알림이 뜨면 무엇을 해야 하는지 |
| VELA Deploy 운영 가이드 | 릴리스 운영자 | 개념 · 절차 · 레퍼런스 | 배포를 어디까지 확대할지 판단하는 기준 |
| VELA Vehicle API | 개발자 | 레퍼런스 · 퀵스타트 | 캠페인 생성 API의 요청 형식 |
| VELA Sense 설치 가이드 | 현장 엔지니어 | 절차 · 진단표 · 사양 | 펌웨어를 수동 복구하는 절차 |

같은 기능이라고 해서 같은 정보를 반복하지 않았습니다.

차량 소유자에게는 **행동**, 운영자에게는 **판단 기준**, 개발자에게는 **인터페이스**, 현장 엔지니어에게는 **복구 절차**가 필요합니다.

따라서 기능 자체가 아니라 **독자가 무엇을 해야 하는가**를 기준으로 설명 범위와 문서 유형을 결정했습니다.

### 품질 기준을 설정 파일로 분리하기

문서 품질 기준을 본문이나 검사 코드 안에 직접 넣지 않고 별도의 설정 파일로 분리했습니다.

설정에는 다음 항목을 정의했습니다.

- 용어집 79개 항목
- 권장·금지 표현을 포함한 스타일 규칙
- 독자와 사전 지식 수준
- 경고 등급 체계
- 문서 구조와 정보 유형에 관한 기준

이 구조를 선택한 이유는 **품질 기준과 검사 로직을 분리하기 위해서**입니다.

문서를 사용하는 조직이나 제품이 달라지더라도 검사 코드를 다시 만드는 대신 설정을 바꾸어 같은 검증 구조를 사용할 수 있도록 했습니다.

### 문서 품질을 자동으로 검사하기

설정 파일을 읽어 전체 문서 44편을 검사하는 스크립트를 작성하고, 정적 사이트를 빌드하기 전에 실행하도록 구성했습니다.

주요 검사 항목은 다음과 같습니다.

- 금지 표현과 독자 수준에 맞지 않는 용어
- 절차의 단계 수
- 안내 상자의 등급과 개수
- 경고의 위치
- 번호 목록 구조
- 정보 유형 선언
- 다이어그램 내부 문장
- 문서 간 중복
- 링크와 앵커의 실재 여부

오류가 하나라도 발견되면 빌드가 실패하고 배포 단계로 넘어가지 않도록 했습니다.

문서를 작성한 뒤 사람이 전체를 다시 확인하는 대신, **명시적으로 정의할 수 있는 규칙은 작성 과정에서 자동으로 검증하도록 만들었습니다.**

### 국문과 영문의 구조 맞추기

한국어 문서를 원문으로 두고 영문 문서를 번역본으로 연결한 뒤, 두 언어의 구조가 서로 어긋나지 않는지도 같은 도구에서 검사하도록 했습니다.

자동으로 대조하는 항목은 다음과 같습니다.
- 제목 단계
- 표의 개수와 구조
- 이미지 개수
- 링크
- 안내 상자의 개수
- 번역되지 않은 한글의 잔존 여부
- Git 이력을 기준으로 원문이 번역본보다 나중에 변경됐는지 여부
- 언어별 금지 표현과 용어집 규칙

문장의 번역 품질 자체를 기계가 판단하도록 하지는 않았습니다. 대신 사**람이 놓치기 쉬운 구조적 불일치는 기계가 확인하도록 역할을 나눴습니다.**

예를 들어 번역 과정에서 표의 일부 행이나 경고 상자를 통째로 누락하면 문장 단위 검토만으로는 발견하기 어렵습니다. 이러한 차이는 두 언어의 문서 구조를 비교해 자동으로 확인하도록 했습니다.

### 검수를 빌드 과정에 연결하기

**문서를 변경해 저장소에 올리는 행위 자체가 검수를 실행하도록 GitHub Actions 파이프라인에 연결하여 검수 과정을 자동화 했습니다.**

![문서를 푸시하면 검수가 먼저 돌고, 통과할 때만 배포되는 흐름](/img/vela-pipeline.svg)

| 단계 | 하는 일 | 실패하면 |
| --- | --- | --- |
| ① 환경 준비 | 저장소를 내려받고 Node 20과 의존성 설치 | 이후 단계가 실행되지 않음 |
| ② 문서 검수 | `_config/`의 설정 파일을 읽어 문서 44편 검사 | **빌드와 배포를 진행하지 않음** |
| ③ 빌드 | 국문·영문 사이트를 정적 HTML로 생성 | 배포하지 않음 |
| ④ 배포 | GitHub Pages에 게시 | 기존 사이트 상태 유지 |


검수 단계에서 오류가 하나라도 발견되면 실패 코드를 반환하고 파이프라인 전체를 중단합니다.
경고는 보고만 하고 빌드를 중단하지 않도록 구분했습니다. 반드시 수정해야 할 오류와 참고해야 할 경고를 구분하지 않으면 경고가 누적되어 결국 아무도 확인하지 않는 상태가 될 수 있기 때문입니다.

### 로컬과 CI의 검수 환경 맞추기

GitHub Actions에서만 검사를 실행하지 않고 로컬의 npm run build 앞에서도 같은 검수 스크립트를 실행하도록 구성했습니다.
로컬 환경과 CI가 **같은 검사 스크립트와 같은 설정 파일**을 사용합니다.
이를 통해 로컬에서는 정상적으로 보이지만 배포 과정에서만 검수가 실패하는 차이를 최소화했습니다.
이 검수 구조는 실무에서 만든 [문서 빌드·검수 도구](./build-tooling.md)의 핵심 개념을 공개 가능한 형태로 축소해 적용한 것입니다.

## 결과

- 제품 4종과 네 종류의 독자를 하나의 제품군 안에서 연결해 44편의 문서 세트를 완성했습니다.
- 같은 기능이라도 독자의 목적에 따라 정보의 깊이와 문서 유형이 어떻게 달라지는지 실제 문서로 구현했습니다.
- 용어집, 스타일 규칙, 독자 정의를 설정으로 분리해 문서 품질 기준 자체를 관리하고 검증할 수 있는 구조를 만들었습니다.
- 국문 원문과 영문 번역본의 구조를 자동으로 비교해 사람이 놓치기 쉬운 번역 누락과 구조 불일치를 확인할 수 있도록 했습니다.
- 검수 스크립트를 GitHub Actions에 연결해 검수를 통과한 문서만 빌드·배포되는 흐름을 구성했습니다.
- 실무 프로젝트에서 설명한 정보 구조 설계와 검수 자동화 방식을 외부에서도 직접 확인할 수 있는 형태로 재현했습니다.
- 네 문서 세트의 전체 내용은 [Sample Docs](/samples)에서 확인할 수 있으며, 각 문서에는 독자와 정보 구조를 어떻게 설계했는지 설명하는 설계 노트를 함께 제공했습니다.
