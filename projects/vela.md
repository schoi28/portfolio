# 가상 제품군 VELA 문서 세트

> 개인 프로젝트 · 2025 · 기획부터 집필까지 단독 진행

## 어려웠던 점

**실무에서 작성한 문서를 공개할 수 없었습니다.**

테크니컬 라이터의 역량을 보여 주려면 완성된 문서뿐 아니라 독자를 어떻게 정의하고, 어떤 기준으로 정보를 구성했는지도 확인할 수 있어야 합니다.

서로 관계없는 문서 몇 편만으로는 이런 설계 과정을 보여 주기 어렵습니다. 따라서 실제 제품군처럼 여러 제품과 독자가 연결된 문서 세트를 만들 필요가 있었습니다.

**문서가 늘어나도 일관된 품질을 유지해야 했습니다.**

제품별로 독자와 문서 유형이 다르면 필요한 설명 수준과 용어, 경고 표현도 달라집니다.

국문과 영문을 함께 관리할 때는 번역 과정에서 표나 안내 상자가 누락되거나, 원문만 수정되고 번역본은 갱신되지 않는 문제도 발생할 수 있습니다.

이러한 항목을 문서가 변경될 때마다 사람이 모두 확인하는 대신, **명확한 기준이 있는 항목은 자동으로 검사하는 구조**가 필요했습니다.

## 해결 방법

### 네 종류의 독자를 위한 문서 작성하기

가상의 차량용 소프트웨어 플랫폼 공급사 VELA와 제품 4종을 설계했습니다.

각 제품의 목적과 사용자에 맞춰 서로 다른 유형의 기술 문서를 작성했습니다.

| 문서 세트 | 대상 독자 | 주요 내용과 문서 유형 |
| --- | --- | --- |
| VELA Drive 앱 사용 설명서 | 차량 소유자 | 차량 관리 앱 사용법 · 튜토리얼 · FAQ |
| VELA Deploy 운영 가이드 | 릴리스 운영자 | 무선 업데이트 배포 · 운영 절차 · 판단 기준 |
| VELA Vehicle API | 개발자 | 차량 데이터·제어 API · 퀵스타트 · 레퍼런스 |
| VELA Sense 설치 가이드 | 현장 엔지니어 | 센서 킷 설치 · 진단 · 문제 해결 · 사양 |

네 문서는 하나의 제품군에 속하지만, 같은 정보를 동일한 방식으로 설명하지 않습니다.

예를 들어 무선 업데이트 기능을 설명할 때 차량 소유자에게는 **업데이트 알림을 받았을 때 해야 할 일**을, 운영자에게는 **배포 범위를 결정하는 기준**을, 개발자에게는 **API 사용 방법**을, 현장 엔지니어에게는 **펌웨어 복구 절차**를 설명했습니다.

이처럼 **기능 자체보다 독자가 수행해야 하는 작업을 기준으로** 정보의 범위와 문서 유형을 결정했습니다.

완성된 국문·영문 문서는 [Sample Docs](/samples)에서 확인할 수 있습니다.

### 문서 품질 기준 정의하기

문서마다 같은 기준을 적용할 수 있도록 품질 규칙을 별도의 설정 파일로 관리했습니다.

| 설정 파일 | 정의한 기준 |
| --- | --- |
| `glossary.csv` | 표준 용어와 금지 표현, 적용 범위 |
| `audience.yaml` | 독자별 사전 지식, 사용하지 않을 용어, 절차 단계 상한 |
| `admonitions.yaml` | 위험·경고·주의·참고의 정의와 문서별 허용 등급 |
| `style-rules.yaml` | 문체와 이미지 규칙, 번역 대조 기준, 검사 면제 조건 |

검사 기준을 코드에서 분리한 이유는 **무엇이 올바른 문서인지 판단하는 기준과 이를 검사하는 기능을 독립적으로 관리하기 위해서**입니다.

제품이나 독자가 달라지면 검사 프로그램을 수정하는 대신 설정을 변경할 수 있도록 했습니다.

또한 기계가 확인할 수 있는 것과 사람이 판단해야 하는 것을 구분했습니다.

예를 들어 금지 표현의 사용 여부나 링크의 유효성은 자동으로 확인할 수 있지만, 설명이 충분히 이해하기 쉬운지 또는 해당 정보가 독자에게 꼭 필요한지는 작성자가 판단해야 합니다.

따라서 **검사 가능한 항목만 자동화하고, 의미와 적절성에 관한 판단은 사람에게 남기는 것**을 원칙으로 삼았습니다.

### 설정을 기준으로 문서 자동 검사하기

설정 파일을 읽어 국문 44편과 영문 44편, 총 88개 언어별 문서 파일을 검사하는 스크립트를 개발했습니다.

검사기는 문장의 의미를 해석하는 대신, 미리 정의된 규칙에 따라 표현과 문서 구조를 확인합니다.

| 검사 영역 | 주요 검사 항목 |
| --- | --- |
| 용어·표현 | 금지 표현, 비표준 용어, 독자 수준에 맞지 않는 용어 |
| 절차·구조 | 절차 단계 수, 번호 목록 구조, 문서 유형 선언 |
| 안전·안내 | 허용된 안내 상자 등급, 마커의 짝, 경고 위치 |
| 참조·이미지 | 링크와 앵커의 유효성, 이미지 대체 텍스트 |
| 문서 관리 | 미확인 값, 문서 간 중복 표현 |
| 번역 정합성 | 제목·표·이미지·링크·안내 상자 구조 비교 |

특히 국문과 영문은 별도의 문서로만 검사하지 않고 서로 비교하도록 했습니다.

- **구조 비교:** 제목 단계와 표·이미지·링크·안내 상자의 개수 등이 다르면 오류로 처리합니다.
- **변경 이력 비교:** 원문이 번역본보다 나중에 수정됐다면 번역 반영 여부를 확인하도록 주의를 표시합니다.
- **언어별 규칙 적용:** 국문과 영문에 각각 다른 용어집과 금지 표현을 적용합니다.

단순한 변경 시각만으로 번역 누락을 확정할 수는 없습니다. 따라서 원문이 더 최근이라는 사실은 **오류가 아니라 확인이 필요한 신호**로 처리했습니다.

### 오류와 주의의 처리 기준 정하기

모든 검사 결과를 동일하게 처리하지 않고 **오류(Error)**와 **주의(Warning)**로 구분했습니다.

| 구분 | 오류 (Error) | 주의 (Warning) |
| --- | --- | --- |
| 판단 기준 | 규칙 위반이 명확한 경우 | 정당한 예외가 있을 수 있는 경우 |
| 예시 | 존재하지 않는 링크, 잘못된 안내 상자 구조, 원문·번역본의 표 개수 불일치 | 절차 단계 수 초과, 중복 문장, 원문이 번역본보다 최근에 변경됨 |
| 처리 방식 | 빌드 중단 | 결과를 보고하고 빌드 진행 |
| 후속 조치 | 문제를 수정한 뒤 재검사 | 작성자가 실제 수정 필요 여부 판단 |

오류가 발생하면 검수 결과를 확인하고 원인을 수정한 뒤 다시 검사합니다.

이때 **문서가 기준을 위반한 경우에는 해당 문서를, 기준 자체가 잘못된 경우에는 설정 파일이나 검사 로직을 수정**하도록 구분했습니다.

모든 항목을 오류로 처리하면 타당한 예외 때문에 빌드가 반복해서 중단됩니다. 반대로 모두 주의로 처리하면 반드시 수정해야 할 문제도 배포될 수 있습니다.

따라서 검사 항목마다 **자동으로 배포를 막아야 하는지, 사람의 확인이 필요한지**를 기준으로 등급을 정했습니다.

### 검수를 빌드·배포 과정에 연결하기

검사기를 수동으로 실행하는 데 그치지 않고 GitHub Actions에 연결해 문서가 변경될 때마다 자동으로 실행되도록 했습니다.

![문서를 고쳐 푸시하면 GitHub Actions가 검수를 먼저 돌리고, 오류가 없을 때만 빌드해 배포하는 과정](/img/vela-pipeline.svg)

검사 결과에 주의만 있다면 내용을 보고하되 빌드는 계속 진행합니다. 오류가 하나라도 발견되면 빌드와 배포를 중단합니다.

| 단계 | 수행 작업 |
| --- | --- |
| 환경 준비 | Node.js 및 필요한 의존성 준비 |
| 문서 검수 | 설정 파일을 기준으로 문서 88개 검사 |
| 사이트 빌드 | 검수를 통과하면 국문·영문 정적 HTML 생성 |
| 배포 | 빌드 성공 시 GitHub Pages 게시 |

로컬 환경에서도 `npm run build` 전에 동일한 검사 스크립트를 실행하도록 구성했습니다.

**로컬과 CI가 같은 규칙과 검사 로직을 사용하므로**, 작성자가 직접 검수할 때와 배포 과정에서 검수할 때의 판단 기준이 일치합니다.

이 구조는 실무에서 설계한 [문서 빌드·검수 도구](./build-tooling.md)의 핵심 원칙을 공개 가능한 프로젝트에 적용한 것입니다.

## 결과

- 가상 차량용 소프트웨어 제품 4종을 설계하고, **네 종류의 독자를 위한 기술 문서 44편을 국문·영문으로 구축했습니다.**
- 같은 제품군 안에서도 독자의 목적에 따라 정보의 범위와 문서 유형을 다르게 구성했습니다.
- 용어·표현·문서 구조·참조·번역 정합성을 **설정된 기준에 따라 자동으로 검사하는 도구**를 개발했습니다.
- 검사 결과를 오류와 주의로 구분해 **반드시 수정해야 하는 문제만 빌드와 배포를 중단**하도록 했습니다.
- GitHub Actions에 검수를 연결해 문서가 변경될 때마다 동일한 품질 기준을 적용하도록 자동화했습니다.
- 문서 작성뿐 아니라 **품질 기준 정의부터 검사·배포까지 연결된 문서 운영 체계**를 공개 가능한 형태로 구현했습니다.

완성된 문서는 [Sample Docs](/samples)에서 확인할 수 있습니다.
