# 문서 빌드·검수 도구 자체 개발

> 자율주행 솔루션 소프트웨어 회사 · Technical Writer · 2025.01 ~ 현재

**사람이 기억하고 조심해야 했던 문서 오류를, 빌드 과정에서 자동으로 검증하도록 바꿨습니다. 실패 조건과 요구사항, 검증 기준을 직접 설계하고 구현 과정에는 AI를 활용했습니다.**

## 어려웠던 점

**문서를 잘 쓰는 것만으로는 막을 수 없는 오류가 있었습니다.**

제품과 버전이 늘어나면서 문서 제작 과정에서도 반복적으로 확인해야 할 항목이 많아졌습니다. 문제는 대부분 사람이 기억하고 직접 확인해야 한다는 데 있었습니다.

- **고객사마다 제공되는 기능이 달랐습니다.** 같은 원본으로 여러 고객사의 납품본을 만들기 때문에 어떤 기능 설명을 포함하거나 제외해야 하는지 작성자가 기억해야 했습니다. 필요한 내용을 빠뜨리면 고객이 구매한 기능을 알 수 없고, 잘못 포함하면 다른 고객사에 제공되는 정보가 노출될 수 있습니다.
- **웹과 PDF를 별도로 만들면 내용이 어긋날 수 있었습니다.** 한쪽만 수정하면 동일한 문서의 두 산출물이 서로 달라집니다.
- **API 스키마와 설정값 목록은 수동으로 관리하기 어려웠습니다.** 제품이 계속 변경되는 상황에서는 문서가 실제 스펙을 따라가지 못할 가능성이 높았습니다.
- **링크와 앵커 오류는 발견하기 어려웠습니다.** 제품과 버전을 합쳐 수백 편의 문서를 운영하면 어떤 참조가 깨졌는지 사람이 일일이 확인하기 어렵습니다.

이 문제들의 공통점은 **문서 품질이 작성자의 주의력에 지나치게 의존하고 있다는 것**이었습니다.

처음에는 MkDocs 같은 공개 정적 사이트 생성기를 사용할 계획이었습니다. 그러나 필요한 커스터마이징이 계속 늘어났고, 배포 환경의 네트워크가 불안정해 완전한 오프라인 동작까지 요구사항에 포함됐습니다.

기존 도구에 계속 예외를 덧붙이는 것보다 필요한 조건을 직접 통제할 수 있는 도구를 만드는 편이 적합하다고 판단해 자체 개발로 전환했습니다.

## 해결 방법

### 실패 조건 먼저 정의하기

코드를 만든 뒤 오류를 찾는 대신, 문서 구조에서 발생할 수 있는 실패를 먼저 목록으로 만들고 이를 구현 요구사항과 검증 조건으로 사용했습니다.

예를 들면 다음과 같습니다.

- 조건부 콘텐츠 마커가 중첩된 경우
- 용어집 대상 용어가 표 안에 있는 경우
- 앵커가 다른 파일의 섹션을 가리키는 경우
- 부록 순서가 바뀌어 용어집 파일의 위치가 달라지는 경우
- 개발 버전이 실수로 고객 납품본에 포함되는 경우

이 과정에서 중요한 것은 코드를 작성하는 일보다 **정상적인 입력과 예외 상황을 빠짐없이 정의하는 것**이었습니다.

무엇을 허용해야 하는지, 무엇을 오류로 볼 것인지, 오류가 발생했을 때 도구가 어디까지 개입해야 하는지를 먼저 명세했습니다.

### 설계와 구현의 역할 나누기

구현 과정에는 AI를 활용했지만, 도구가 어떤 문제를 해결해야 하는지와 어떤 방식으로 동작해야 하는지는 직접 결정했습니다.

| 직접 설계한 것 | 구현에 활용한 것 |
| --- | --- |
| 조건부 콘텐츠의 기준: 고객사 · 내부/외부 · 기능 | AI를 활용한 구현 코드 작성 |
| 적용 범위: 섹션 · 페이지 · 포맷 | 파싱 및 처리 로직 |
| 조건부 콘텐츠 마커 문법 | 빌드 스크립트 |
| 검수해야 할 오류의 종류와 우선순위 | 개별 검사 로직 |
| 산출물이 선언된 노출 범위와 일치하는지 검증하는 방식 | |
| 자동 수정을 어디까지 허용할지 | |
| 용어집을 자동 적용하지 않고 옵트인 방식으로 운영할 것인지 | |
| 파일을 위치가 아닌 이름을 기준으로 찾는 방식 | |
| MkDocs에서 자체 개발로 전환하는 결정 | |

여기서 핵심은 구현 자체보다 **무엇을 시스템이 책임져야 하는지 결정하는 일**이었습니다.

예를 들어 고객사 정보가 섞이는 오류를 가장 위험한 실패로 정의하지 않았다면, 산출물의 실제 내용이 선언된 노출 범위와 일치하는지 검사할 이유도 없습니다.

마찬가지로 자동화 도구가 문서 내용을 임의로 수정하면 결과를 신뢰하기 어렵다고 판단했기 때문에, 발견한 문제를 자동으로 고치는 범위도 제한했습니다.

### 반복되는 실패를 검사 규칙으로 바꾸기

| 실패 지점 | 해결 |
| --- | --- |
| 고객사 정보 혼입 | 각 콘텐츠의 노출 범위를 선언하고, 빌드 결과가 선언된 범위와 일치하는지 검증. 고객사·내부/외부·기능 세 축을 섹션·페이지·포맷 단위로 제어 |
| 웹·PDF 불일치 | 하나의 원본에서 웹과 PDF를 함께 생성. PDF는 렌더링 후 압축해 용량을 약 44% 절감 |
| API 문서 노후화 | OpenAPI 스펙에서 엔드포인트와 스키마 문서를 생성하고, 추가·삭제·타입·제약 조건·enum 값 변경을 리포트로 산출 |
| 링크·앵커 파손 | 링크 대상 파일과 앵커가 실제로 존재하는지 파일 간 교차 검증 |
| 독자가 이해하기 어려운 용어 | 용어집에 등록한 용어의 첫 등장에 호버 툴팁을 적용. 모든 용어를 자동 처리하지 않고 지정된 항목만 적용 |
| 개발 버전 오납품 | 기본 빌드 대상을 개발 버전을 제외한 최신 릴리스로 설정하고, 개발 버전은 명시적으로 선택해야 포함되도록 제한 |

### 비작성자도 사용할 수 있게 만들기

명령줄 사용에 익숙하지 않은 구성원도 같은 방식으로 빌드하고 검사할 수 있도록 웹 기반 GUI를 만들었습니다.

빌드와 검사가 동시에 실행돼 파일 상태가 충돌하지 않도록 잠금 처리도 추가했습니다.

도구를 만드는 것뿐 아니라 **누가 사용하더라도 같은 결과를 얻을 수 있는 작업 흐름을 만드는 것**까지 범위에 포함했습니다.

## 산출물

| 도구 | 역할 |
| --- | --- |
| 정적 사이트 생성기 | 하나의 원본에서 웹·PDF를 생성하고 고객사별 콘텐츠를 조건에 따라 조립 |
| 검수 도구 | 링크·앵커 교차 검증, 조건부 콘텐츠 마커 검증, 산출물과 선언된 노출 범위의 일치 여부 검사 |
| API 문서 생성기 | OpenAPI 스펙을 기반으로 문서를 생성하고 변경 사항을 리포트로 출력 |
| 빌드 GUI | 명령줄 없이 문서 빌드와 검사를 실행 |
| 기여자용 문서 | 도구 설정 및 문서 작성 방법을 설명하는 설정 가이드와 작성 가이드 |

## 결과

- 솔루션 전체와 통합 PDF를 포함한 가장 큰 범위의 납품본도 **설정을 선택한 뒤 한 번의 빌드로 약 2분 안에 생성**할 수 있게 됐습니다.
- 고객사별 콘텐츠 범위를 작성자가 기억해 확인하는 대신 **빌드 과정에서 실제 산출물을 검증**하도록 바꿨습니다.
- 웹과 PDF를 하나의 원본에서 생성해 두 포맷을 별도로 관리하면서 발생하는 불일치를 줄였습니다.
- 하나의 제작 환경에서 **3~4개 제품의 문서 작업을 병행**할 수 있게 됐습니다.
- OpenAPI 기반 문서 생성과 변경 리포트를 통해 제품 스펙과 API 문서의 차이를 확인할 수 있도록 했습니다.
